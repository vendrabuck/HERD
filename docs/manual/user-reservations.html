Reserving equipment

A reservation is a time-boxed claim on one or more devices. Making one is how you say "this gear is mine from Tuesday to Friday." This is the single most common thing you'll do in HERD.

The one-sentence version

Go to Reservations → New reservation, fill in a purpose, a start and end time, tick the devices you want, and submit. Everything below is just detail on top of that.

Home base

Your reservations list

When you land on Reservations, you see your own bookings. Each row is one reservation, colour-coded by where it is in its life. Four of the column headings sort the list, every row has a checkbox so you can act on several at once, and an admin can switch the list to everyone's bookings.

  1. New reservation. The button that starts everything. Opens the form in step Create a reservation.
  2. My Reservations. Just yours. This is the default view; the label reads All Reservations once an admin ticks the checkbox in item 7.
  3. Calendar. Everyone's bookings on a timeline — use it to find a free window before you book.
  4. Status badge. The colour tells you what's happening. Full key is just below.
  5. The checkbox column. Tick rows to act on several at once; the header checkbox selects every row on the current page (its accessible name is "Select all reservations on this page"). Ticked rows turn pale blue. The selection is dropped when you change page, change the sort, or switch the All reservations view.
  6. The selection bar. Appears as soon as one row is ticked: "N selected", then Cancel selected and Release selected, then Clear selection. Each action is checked row by row with the same rule as the per-row buttons. When no ticked row qualifies, that button is disabled and a note beside it says why, for example "None of the selected reservations can be cancelled: 1 already finished, 2 not yours." Clicking an action opens one confirmation, titled Cancel Reservations or Release Reservations, whose text counts what will run and what will be skipped: "Cancel 3 reservations? This releases their devices and cannot be undone.", or "Cancel 2 of the 3 selected reservations? This releases their devices and cannot be undone. 1 will be skipped: 1 already finished." Release says "This ends them early and frees their devices." The skip reasons are "already finished", "not active" (Release only), and "not yours". The confirm button reads "Cancel 3 reservations" or "Release 1 reservation"; the dismiss button reads "Keep reservations" or "Do not release". HERD then runs the ordinary cancel or release for each row, one at a time; there is no bulk endpoint. A success toast says "Cancelled 3 reservations"; with failures you get an error toast such as "Cancelled 2, failed 1", followed by the server's reason when every failure shares one. Rows that succeeded leave the selection; rows that failed stay ticked so you can retry or inspect them.
  7. All reservations admin only. A checkbox beside the tabs and the count. Tick it to switch the list from your own bookings to everyone's; the list returns to page one. This is what the Owner column is for. Admins can Cancel another user's reservation from here, but Release is only ever offered to the owner.
  8. Sortable headings. Owner, Status, Period, and Purpose are buttons. The first click sorts ascending, the second descending, and the third clears back to the default order, newest created first. The active heading shows an up or down chevron. Period sorts by start time; Status sorts alphabetically by status name. Changing the sort returns you to page one, and the choice is remembered with your other saved preferences. ID, Topo ID, Topology, and Devices do not sort.

The last column holds a green Release and a red Cancel text button, shown by the same rule as the bulk actions: Release on an ACTIVE reservation you own, Cancel on any PENDING, PENDING_PROVISION, or ACTIVE reservation you own or, as an admin, anyone's. Release acts at once. Cancel asks first, in a dialog titled Cancel Reservation: "Cancel this reservation? This releases its devices and cannot be undone.", with the buttons Cancel reservation and Keep reservation.

The main event

Create a reservation

Click New reservation. You get this form. Nothing is reserved until you submit.

  1. Purpose. A short human label so people (and the report) know what this booking was for. "HA failover regression," not "test."
  2. Start & end. Your time window. The reservation is dormant until the start time passes, then activates on its own.
  3. Devices. Chosen beforehand on the topology canvas; this form just shows how many you picked. There's no separate device picker in the reservation form itself.
  4. Reserve. Submit. The new reservation appears in your list immediately.
  5. Dynamic instances. Only useful if your admin has created dynamic templates: add rows to book hypervisor-backed instances alongside (or instead of) real devices. Coming from the topology canvas, placeholder nodes prefill this block — see Dynamic resources.
  6. Purpose category. Optional, separate from the free-text Purpose above: a short, fixed list (QA regression, support case replication, feature development, customer demo/POC, training, performance benchmark, other, or whatever your admin has configured) that the utilization report can chart. Defaults to Unclassified and never blocks submission; you or an admin can set or change it later from the detail modal, in any status.
AI suggestion (when your admin has it turned on)

Once you have typed a few words of purpose or picked a topology, the still-untouched category dropdown prefills itself with the AI's top guess, and a small Suggested: <category> <NN>% line appears underneath with the top three categories as percentage chips. Pick a category yourself at any point and the suggestion stops overwriting it, even if a later, different suggestion comes back. A failed suggestion call just shows a muted "Suggestion unavailable" and never blocks or delays submitting the form. The value you submit, suggested or hand-picked, is recorded as your own choice either way.

Conflict on submit?

Conflicts aren't caught before you submit; if a device you picked is exclusive and already booked in your window, the reservation is rejected at submit time and HERD tells you exactly which devices clashed. Adjust your window (check the calendar) or drop the conflicting device on the topology canvas, then resubmit.

The colour code

Cancel vs Release

Cancel stops a future or current reservation and frees its devices. Release ends an ACTIVE reservation early: you're done before your end time and want to hand the gear back now. Both free the devices immediately. Who may act differs: the owner or an admin may Cancel, so an admin sees Cancel on another user's reservation; only the owner may Release, so an admin who does not own the reservation sees no Release button.

A distinction that bites people

Exclusive vs shared devices

Exclusive

DUTs and individual test instruments. One reservation at a time. Booking it for an overlapping window fails with a conflict. Status flips to RESERVED while a reservation that is being provisioned or is ACTIVE holds it; a future PENDING booking does not flip it.

Shared

Network infrastructure (switches, shared fabrics). Many reservations at once. Status never changes on reserve or release — it's plumbing everyone uses.

Which bucket a device falls in is decided by its template, not by you. You don't choose — you just see the effect when a conflict (or no conflict) happens.

Drilling in

The reservation detail modal

Click any row to open its detail view. Five tabs:

  1. Details — the basics: id, purpose, dates, status. The default tab.
  2. Inventory — the devices in this reservation. Expand a device to see its ports and what each is cabled to.
  3. Routes — for DUT-to-DUT pairs, the hop-by-hop path through the L1 switches. Green = reachable, red = not.
  4. Wiring — the per-connection status of the L1 wiring HERD applied to the hardware, with a Retry failed action while the reservation is active. Full walkthrough in Live editing.
  5. Schedule — inline-edit the end time and purpose without rebooking.
  6. Dynamic instances — if the reservation carries dynamic requests, the Details tab lists them grouped by template with a count. The instances themselves appear once the reservation is ACTIVE.
  7. Purpose category — you (the owner) or an admin can set or change this from the same list of categories offered at creation, in any status including COMPLETED, CANCELLED, and FAILED, so past reservations can be classified retroactively. Anyone else sees it as a read-only tag. If the reservation carries an AI suggestion, a muted AI suggested: <category> <NN>% line sits under the category row (the model's reasoning shows as a tooltip on hover), with a "(dismissed)" marker once an admin has dismissed it. This line is read-only here: an admin accepts, overrides, or dismisses a suggestion from the Purpose Review page, not from this modal.
  8. Classify now admin only. A small button directly under the Purpose category row (and under the AI suggested line, when there is one), shown on a COMPLETED, CANCELLED, or FAILED reservation that has no suggestion yet. It asks the classifier for a suggestion for this one reservation, the same call Classify history runs over the whole backlog; while it runs the button reads "Classifying...". On success a toast says "Suggested category: <category>." and the button goes away. Any other outcome is a plain sentence: "Classification timed out. Check that the AI orchestrator is responding, then try again.", "The AI orchestrator could not take the request right now. Check its status, then try again.", "Classification failed. Check the AI orchestrator logs, then try again.", or "The AI orchestrator refused the request. Check that its internal token matches this service." Three refusals: "Purpose classification is disabled." when the feature is off; "This reservation already has a suggestion. Review it on the Purpose Review page."; and "This reservation is not ready to be classified." for a reservation that ended before classification existed and was never swept or backfilled (run Classify history first). On either of the last two the button goes away.
Need to add a device mid-run?

You (the owner) or an admin can hit Edit Resources on an active reservation to add or remove devices on the fly. Added exclusive devices get a conflict check; removed ones are released back to AVAILABLE.

Re-wiring a live reservation

On an ACTIVE reservation you own, the tab bar also shows Edit topology. It opens the reservation's private fork in the editor's live-edit mode — your changes never touch the shared master topology, and a PENDING reservation offers no topology editing at all (its fork doesn't exist until activation). After the reservation ends, the button becomes View as-built. The whole flow is step 4, Live editing. The green Release and red Cancel buttons at the bottom of the Details tab follow the same rules as the list: Release on your own ACTIVE reservation, Cancel on any PENDING, PENDING_PROVISION, or ACTIVE reservation you own or, as an admin, anyone's. Cancel asks first with the same "Cancel this reservation?" dialog.

Finding a free window

The reservation calendar

Click the Calendar tab. It's a Gantt-style timeline of everyone's reservations (filtered to gear you can see), so you can spot a gap before you try to book.

  1. Day / Week / Month. Zoom the timeline to the granularity you care about.
  2. Status filter chips. Dim out COMPLETED and cancelled bookings to declutter and see what's actually live.
  3. Click any block to open that reservation's detail modal — even other people's, so you know who to ask if you need their slot.
