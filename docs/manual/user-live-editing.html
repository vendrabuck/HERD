Live-editing a reservation

Once a reservation is ACTIVE, you can re-wire its topology while it runs. You're not editing the shared master diagram — you're editing the reservation's own private fork, and HERD applies your changes to the real hardware.

The one-sentence version

Open an active reservation, click Edit topology, re-wire the canvas, and hit Commit to reservation — your edits land on a private copy, never on the master topology, and the Wiring tab shows you whether each cross-connect actually took.

The mental model

What a fork is

The moment your reservation activates, HERD gives it a fork: a private working copy of the topology it was created from. Everything you do in live-edit mode happens on that fork:

  • It exists from activation onward. A PENDING reservation has no fork yet, so there is nothing to edit before it goes active.
  • It's yours. Only the reservation owner (or an admin) can open it, and it's editable only while the reservation is ACTIVE.
  • It has its own version history. Every commit appends a fork version. The fork history panel lists them (newest first, with author and timestamp) but is view-only — no preview, diff, or restore, unlike a standalone topology's history.
  • It outlives the reservation — as a frozen, read-only as-built record.

Read this if you used the old behavior

Two changes that will surprise you

Live edits no longer touch the parent topology

Editing during a reservation used to modify the shared master topology and clutter its version history. It doesn't anymore. Live edits go to the reservation's fork and append fork versions only — the master template stays exactly as saved, for everyone. If you relied on live edits to update the master, save the master separately from the topology editor.

PENDING reservations no longer offer topology editing

The fork exists only from activation onward, so a PENDING reservation's detail modal shows no Edit topology button at all. Previously, editing a not-yet-active reservation mutated the shared parent topology; that path is gone. Wait for the reservation to activate, then edit its fork.

Getting in

Opening live-edit mode

Open your ACTIVE reservation

Click its row on the Reservations page to open the detail modal.

Click Edit topology

The blue-outlined button in the tab bar. It's there only if you own the reservation (admins can open the fork too) and the reservation is active.

You land on the canvas, in live-edit mode

The editor loads the reservation's fork, not the parent topology, and a blue banner marks the mode.

  1. The live-edit banner. Shows the device count and the autosave status. Everything else on the canvas works exactly like the normal editor: drag devices, draw or remove L1/L2/L3 links, same red-edge checks.
  2. Autosave status. Cycles through "Saving draft…" and "Draft saved" as you work. See below.
  3. Commit to reservation. The explicit save. Disabled while any edge is red — same rule as reserving. See Committing.

Work in progress is safe

Drafts & autosave

As you edit, your changes autosave as a loose draft a moment after you stop making them — the banner flips from "Saving draft…" to "Draft saved". A draft is stored without touching the hardware or the fork's version history, so you can close the tab mid-thought and pick the edit back up later.

  • "Draft saved" does not mean applied. Nothing reaches the reservation or the hardware until you commit.
  • "Draft save failed" in red means the autosave didn't land (usually a network blip). Your canvas is still intact; keep the tab open and commit, or check your connection.

Making it real

Committing your wiring

Click Commit to reservation. HERD reconciles the fork in one transaction: connections you removed are released, connections you added are built (release before build), and a new fork version is appended. The fork is the source of truth for wiring: committing is exactly what reconciles your L1/L2/L3 wiring to the hardware, not a side effect of the reservation's device set.

A toast reports the result — "Fork saved as vN" with released, built, and unchanged counts — and expands to list the exact connections released and built.

Red edges block the commit

Same as reserving: if any edge has no physical path, the commit button is disabled and the banner tells you how many edges to fix or remove. The server applies the same check, so there's no way around it.

When someone got there first

Port conflicts

Switch ports are a shared resource. If your wiring would claim a port that another active reservation already holds, the save is refused and this dialog appears:

  1. Each blocking claim, spelled out. One row per conflict: the port, the device it's on, and the reservation currently holding it. Use the reservation id with the calendar to find out whose it is and when it frees up.
  2. Nothing is lost. Your drawing stays on the canvas exactly as you left it. Re-wire the conflicting connections onto free ports (or wait the other reservation out) and commit again.

Did the hardware take it?

The Wiring tab

Committing records your intent. HERD then applies your wiring to the actual switches one connection at a time, layer by layer, and the reservation detail modal's Wiring tab shows how each one went, grouped into sections: L1 cross-connects (switch port pairs), L2 VLAN memberships (each port and its allocated VLAN), and L3 route pins (each L3 switch's pinned routes).

  1. A healthy connection. The switch, the layer-specific detail (an L1 port pair, an L2 port and VLAN, or an L3 route count), an ACTIVE status, and the attempt count. Released rows show a gray RELEASED instead.
  2. A failed connection. The status goes red and the driver's actual error is printed underneath. Your saved wiring is not rolled back — the intent stays durable, only the hardware apply failed.
  3. Retry failed. Reattempts every retryable failed row across all layers at once; a toast summarizes how many reconnected, released, are still failing, or are not retryable. The button appears only while the reservation is ACTIVE and something is actually retryable.
Most failures fix themselves

A driver timeout or a switch login blip is transient: HERD auto-retries failed connections in the background with backoff. Reach for Retry failed when you don't want to wait.

When retrying won't help

A failed connection marked not retryable can't be reapplied as recorded — its cabling path changed under the reservation, so the row explains that retrying is pointless. The fix is to re-save the fork wiring (open live-edit mode and commit again), which re-resolves the path against current inventory. Then retry.

The paper trail

After the reservation ends

Once the reservation is COMPLETED, CANCELLED, or FAILED, the fork freezes into the immutable as-built record: the last wiring the reservation was actually reconciled to.

  • The detail modal's button becomes View as-built. It opens the same fork in the editor, read-only, under a gray "As-built record (read-only)" banner. Nothing can edit it after this point.
  • The Wiring tab stays readable as part of the record — but the Retry failed action is gone, since it's offered only while the reservation is active.
Why keep it?

The as-built record answers "what was this lab actually wired as when the test ran" — months later, without archaeology. It's the reservation's audit trail, not a template; clone the master topology if you want to run the same lab again.
