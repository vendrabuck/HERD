The short version

What 0.1.0 is

HERD is a lab reservation and topology-management platform built lab-first, for organizations that run a hardware lab and cannot answer two questions: "do we have a lab, and how do I use it?" and "what was done in the lab, by whom, on what, for how long?" Any engineer can browse live inventory, build a topology, and reserve equipment without tribal knowledge; leadership gets utilization reporting with CSV export to defend lab budget.

The differentiator is the AI topology pipeline: you describe a need in plain language, an LLM proposes a wiring plan against live inventory, you review it as ghost nodes on the canvas, and committing transactionally creates the topology, books the reservation, and can push per-device configuration.

0.1.0 is the first tagged release. It consolidates 296 merged pull requests into a coherent platform.

The contents

What shipped

01

AI topology generation with human review

Natural-language prompts plus optional PDFs, tech-support tarballs, or text files produce role-based device proposals rendered as PROPOSED ghost nodes. Accept transactionally creates the topology and books the reservation, with an optional per-device config push. Feature-gated by a configured LLM provider: an Anthropic backend and an OpenAI-compatible backend covering vLLM, Ollama, LM Studio, OpenAI, and Azure OpenAI. Generate with AI →

02

Reservation lifecycle and editable forks

PENDING to PENDING_PROVISION to ACTIVE to COMPLETED, with cancelled and failed branches, automatic activation and expiration, and conflict detection for exclusive devices. On activation a reservation gets an editable fork of its parent topology; edits autosave as drafts and a commit reconciles release-before-build. A port claim colliding with another active reservation is refused with a conflict naming the blocker, and at teardown the fork freezes to an immutable as-built record. Live editing →

03

Automatic L1/L2/L3 provisioning

Reservation lifecycle events drive Layer 1 port cross-connects, Layer 2 VLAN creation and membership with fabric-aware VLAN ids, and Layer 3 static routes pinned from the switch's latest config version, so teardown removes exactly what was applied. After a fork save, wiring is reconciled connection-driven at all three layers against per-connection ledgers, with background auto-retry and manual retry that is direction-aware, so a stuck disconnect can finish even after a reservation ends.

04

Driver sandbox

Admin-uploaded packages (.zip or .tar.gz, SHA256-cached) run as a subprocess under POSIX rlimit caps and are validated for required methods before execution. Drivers may publish their own JSON Schema config vocabulary, preferred over the connection-type registry at the configure boundary. Per-command execution transcripts back the config-apply and AI-confirmation surfaces.

05

Encrypted credential store

Named secrets under AES-GCM envelope encryption, with a key-encryption key supplied by environment; the service refuses to boot without a valid one, so there is no source-visible default. Online key rotation with a two-key window, ACL-gated reveal, and an internal retrieval surface for automated provisioning.

06

Dynamic hypervisor-backed resources

A dynamic template type materializes an instance from a registered hypervisor at reservation time through a recipe driver, records it in an idempotent instance ledger, and surfaces it as a real inventory device. A reservation carrying a dynamic request activates only once every instance exists, and a provisioning timeout prevents a lost callback from stranding a booking.

07

Authentication and access control

Local or LDAP/Active Directory sign-in with three roles: user, admin, superadmin. LDAP users JIT-provision on first bind while superadmin rows stay local. Device-group membership gates non-admin visibility; resource-level ACL grants layer narrower carve-outs on top.

08

External API and webhooks

A stable, versioned /api/v1 facade for CI/CD and test automation to reserve and release devices, authenticated with admin-minted API tokens whose role can never exceed their principal's, forwarding caller identity so RBAC and visibility rules apply as they do interactively. Lifecycle webhooks are HMAC-SHA256 signed, at-least-once with retry and backoff, idempotent on event_id, and dead-lettered on exhaustion.

Also in this release

  • Zero-database first-startup config UI, whose saved values outrank env vars. First-day setup →
  • Utilization reporting by user, device, topology type, day, and group, with CSV export and a fleet-utilization view. Reporting →
  • Multi-channel notifications, in-app bell plus email, Slack-style chat, and HMAC-signed webhook, driven by durable consumers. Notifications →

Under the floor

Architecture

HERD is a uv workspace of twelve FastAPI microservices behind a Traefik v3 gateway that terminates TLS and routes each /api/<service> path prefix. Every service owns its own PostgreSQL 16 schema, its own Alembic migration chain, and its own test suite; there are no cross-schema foreign keys or joins, so services reference each other only by UUID validated over HTTP at the boundary.

Asynchronous work flows over NATS JetStream. Every state-change event is written to a per-service transactional outbox in the same database transaction as the state change, then drained to NATS by a background relay with broker-side and consumer-side dedup. Consumers are durable pull consumers with service-scoped dead-letter subjects on a dedicated DLQ stream, so a messaging outage delays delivery rather than dropping a provisioning or notification event.

The frontend is React 19 with TypeScript and Vite, using Zustand and TanStack Query for state and a React Flow canvas for topology editing.

What it was tested against

Quality bar

  • Over 3,300 backend unit tests across the thirteen suites, on in-memory SQLite.
  • OpenAPI contract snapshot tests that fail on any public-API shape change.
  • 173 cross-service integration tests against a live stack.
  • 130 end-to-end browser tests: 123 Selenium, 7 Playwright.
  • Around 480 frontend tests via vitest, plus Locust load tests. Coverage targets 85% or higher per backend service.

CI gates main with a branch-protection ruleset: the backend and frontend jobs (lockfile-drift check, lint, format check, tests, coverage, frontend build) must pass before merge. An advisory integration job boots the full ephemeral stack for the contract and integration suites, and a scheduled nightly workflow runs the heavier suites PR CI skips. CodeQL runs on pull requests, pushes to main, and a weekly cron.

The honest part

Known boundaries

These are limits of 0.1.0, not bugs. If you hit one, the answer is "not yet", not "file a ticket".

  • Initial provisioning and teardown are still device-set-driven, not connection-driven. The connection-driven reconcile at all three layers ships for the fork-save path; unifying initial provisioning and teardown through it is in progress under ADR 0009 (phases 6 and 7).
  • The per-connection wiring-status surface is Layer 1 only. The Layer 2 and Layer 3 wiring-status view lands with ADR 0009 phase 8.
  • Dynamic resources and AI recipe authoring are feature-gated. Recipe authoring is dark by default behind AI_RECIPE_AUTHORING_ENABLED. Dynamic template authoring is API, seed, or bulk-import only; the template editor UI has no dynamic option yet.
  • Resource-level ACL grants have no management UI. Admins drive the ACL API directly.
  • Driver packages are trusted code. The execution sandbox applies POSIX setrlimit caps (address space, CPU) and runs each package as a subprocess, but this is resource bounding, not OS-level isolation.

Some manual pages describe screens that only appear when a feature is configured, for example the AI Assistant tab and the Use AI button. On an install with no LLM provider configured, those surfaces are hidden and the AI endpoints return 503. That is the feature gate, not a broken deployment.
