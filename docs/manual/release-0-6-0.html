Release 0.6.0

The version this manual documents. 0.6.0 makes the two screens you live in do more: the reservations list sorts, cancels a booking before it is active, and runs Cancel and Release over a ticked set of rows; the Inventory page filters by status, template, and topology; an admin can classify one reservation's purpose with Classify now. Underneath, every reservation status write is race-safe, a device cannot be deleted while wiring still depends on it, AI generation only picks devices the lab can actually wire, and every part of the stack now says what version it is running.

The short version

What 0.6.0 is

0.5.0 taught HERD Layer 3. 0.6.0 is about the screens and the writes behind them. On the Reservations page the Owner, Status, Period, and Purpose headings sort, a booking can be cancelled while it is still PENDING, and ticking rows gives you Cancel selected and Release selected with one confirmation that says what will be skipped and why. On the Inventory page three selects beside the search narrow the list by status, template (shown with vendor and model), and topology, and an expanded row stays open when the list refreshes under it. An admin can ask for a purpose suggestion on one finished reservation with Classify now, from its detail modal.

Under the floor, every reservation status transition is now a compare-and-swap, so a cancel that lands mid-create can no longer leave a reservation ACTIVE and never wired, and a future PENDING booking holds no device. Deleting a device is refused while a live reservation's wiring runs through it or while any cable still names it. AI generation asks cabling which candidate devices are connected before it proposes anything, and commit checks again before a reservation is created. The version shows on the login page and in the header, and an admin About page lists the version and build of the frontend and all twelve services.

The contents

What shipped

01

A reservations list that works at scale

The Owner, Status, Period, and Purpose headings sort; a third click returns to the default order, and the choice persists. A booking can be cancelled before it is active. Tick rows and use Cancel selected or Release selected: one confirmation says how many will run and what will be skipped and why. An admin can cancel another user's reservation; only the owner can release. The list → Status and who moves it →

02

Reservation status writes are race-safe

A cancel that lands while a reservation is being created can no longer leave it ACTIVE and never wired. A future PENDING booking no longer touches device status. Back-to-back bookings of one exclusive device no longer leave it AVAILABLE under a live booking. A dynamic instance that teardown retired is never brought back by a late create. Reading the status badges →

03

Inventory page filters

Status, Template (shown with vendor and model), and Topology selects sit beside the name search, with a Clear filters control. The choices persist between visits, and an expanded device row stays open when the list refreshes under it. The Inventory page →

04

Device delete refuses while wiring depends on it

A device cannot be deleted while it is a transit hop on a live reservation's wiring, or while any cable still names it. There is no force option. The device page keeps the refusal on screen with a link to Connections. Can't delete a device → Deleting a device →

05

AI generation picks devices that can be wired

Generation asks cabling which candidate devices are connected and searches for an assignment that satisfies every proposed link; commit checks wireability again before the reservation is created. Separately, a reservation assistant turn whose tools already ran is kept when the model returns no text, times out, or the provider fails, so the record of what it did survives. Version and build visibility

Also in this release

  • An admin can classify one reservation's purpose from its detail modal with Classify now. The detail modal →
  • Hardened: the auth service authorizes on the lower of the token's role claim and the account's current role; the database and message-broker host ports bind to loopback only; a device node on a topology canvas keeps a fixed set of fields and never field_data; the execution service checks each reservation lifecycle event with the reservations service before acting; every device-scoped inventory read and the topology import follow device-group visibility; every CSV export neutralizes spreadsheet formulas. Three of these were published as security advisories with this release; a deployment on 0.5.0 or older should upgrade, run make migrate-cabling so stored canvases are scrubbed, and rotate any device password that was saved on a topology canvas by an admin.
  • Config apply is refused on a driver whose connection type cannot configure, and a driver's raw exception text no longer reaches a stored error. Scheduled apply →
  • Outbound webhooks (the /api/v1 facade) can subscribe to device.health_transition.
  • Message-bus consumers retry on an explicit delay schedule and keep a message alive while its handler runs, so a slow webhook receiver is not handed the same event twice.
  • A streamed assistant answer always ends in a done or an error frame.
  • A new task-oriented guide to the simulated-hardware tiers: docs/SIMULATED_LAB_GUIDE.md.
  • Developer facing: the frontend toolchain floor (npm 11.11.0) is pinned, an opt-in AI generation evaluation harness exists, the JSON log formatter emits every extra field with key-name redaction, and the unused HEALTH_POLL_MINIMUM_INTERVAL_SECONDS setting was removed.

The architecture is unchanged from 0.1.0: twelve FastAPI services behind Traefik, one PostgreSQL schema and migration chain per service, NATS JetStream with transactional outboxes for events. The 0.1.0 architecture section still describes it.

What it was tested against

Quality bar

Measured at the tagged commit by the full make everything run on 2026-10-01:

  • 6,169 backend unit tests across the 13 suites plus the repo-root suite; backend line coverage 96.7% with every service at 95% or higher.
  • 1,636 frontend tests via vitest, 91.0% line coverage.
  • 12 OpenAPI contract snapshot suites.
  • 230 cross-service integration tests: 221 run in the main pass, the 6 LDAP-mode tests run in their own phase against the gate stack, and 3 are gated on an AI provider or other stack configuration.
  • 178 end-to-end browser tests, run twice: 130 on the unseeded stack (48 device-gated skips) and 174 again on the seeded stack with no unexpected skip allowed (4 exempt).
  • 41 live-LDAP tests against the checked-in infra/ldap-test directory, hard-required in the gate.
  • 28 driver tests against real FRRouting and Nokia SR Linux nodes in the checked-in lab, run on every pull request and inside the gate.
  • Nine Postgres-live suites against the gate database, hard-required: the seven from 0.5.0 plus two new this release, the reservation status compare-and-swap race (issue #899) and the sort-by-status ordering (issue #902).
  • Load: 20 simulated users for one minute, 655 requests, 0 failures, median 13 ms, p95 250 ms.

New in CI this release: the frontend job reruns npm install and fails on any package-lock.json diff (issue #885). The release gate is unchanged: a clean full validation run (lint, format check, every unit suite with coverage, frontend build, contract snapshots, integration, end-to-end, and load, against a rebuilt ephemeral stack) at the tagged commit, plus the same branch-protection ruleset on main described on the 0.1.0 page. The ruleset also covers release/* branches.

The honest part

Known boundaries

These are limits of 0.6.0, not bugs. If you hit one, the answer is "not yet", not "file a ticket". One of 0.5.0's, Classify now for a single reservation being an API call only, closed in 0.6.0: see the detail modal.

  • Network element provisioning (anchored VLANs) is a later phase. Elements are canvas objects today: they attach, save, validate, and diff, but nothing is provisioned from them.
  • Manual wiring retry is not exposed through the external API. The /api/v1 wiring-status passthrough is deliberately read-only; retrying a failed connection is an interactive, owner-gated action.
  • A failed VLAN removal is logged, not blocked on. If delete_vlan fails on last-free, the allocation is already released and the empty definition lingers on the switch until an operator removes it. Bounded lingering is the accepted trade.
  • AI recipe authoring is dark by default. Unchanged from 0.1.0: it stays behind AI_RECIPE_AUTHORING_ENABLED.
  • Driver packages are trusted code. Unchanged from 0.1.0: POSIX setrlimit caps and a subprocess boundary are resource bounding, not OS-level isolation.
  • Purpose classification is off by default. It needs a configured AI provider and AI_PURPOSE_CLASSIFICATION_ENABLED. A suggestion never writes the confirmed category by itself; an owner or an admin does.
  • Config-version history for a device outside your groups answers "Device not found". The same answer as the device page gives. That is the visibility rule catching up, not a missing device.
  • A route that names a virtual router needs a driver that declares it. Only a driver declaring supports_vrf drives one; on any other driver the route is refused as l3_vrf_unsupported and stays visible in the Wiring tab until the intent or the driver changes. The shipped frr_l3 driver declares it.
  • The assistant's web sources are off by default. They stay behind AI_DOCS_WEB_ENABLED and are limited to operator-allowlisted https prefixes; the built-in manual and any configured folders are on.
  • A delete right after a cancel can still precede teardown. Execution tears down a cancelled reservation's wiring asynchronously, so a device delete issued in that window can still be refused as in use for a moment. The delete guard answers 503 when cabling or reservations cannot be asked.
  • Webhook delivery is at-least-once. A crash while a POST is in flight can still deliver the same event again. Receivers should treat an event id they have already seen as a repeat.
  • Classify now can show on a finished reservation that is not yet eligible. A reservation that ended before classification existed and was never swept or backfilled shows the button and answers "This reservation is not ready to be classified." Run Classify history first.
  • The Period column sorts by start time. There is no heading that sorts by end time in the UI; the API accepts sort_by=end_time.
  • The About page's skew check is strong evidence on a clean tagged build and weak on a dirty one. The build string names the commit an image was built from, not its bytes, so two images built from the same dirty tree read as identical.

Some manual pages describe screens that only appear when a feature is configured, for example the AI Assistant tab, the Use AI button, the LDAP Sync page's actions, the Purpose Review queue, and the Classify now button. On an install where the feature is off, those surfaces are hidden or inactive. That is the feature gate, not a broken deployment.
