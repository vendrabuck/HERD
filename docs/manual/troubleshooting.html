Troubleshooting

Find your symptom, get the fix. Almost everything here is something you can resolve yourself or with a one-line ask to an admin — no support ticket required. Organised by what you actually see on screen.

How to use this page

Scan the headings for the thing that's happening to you, then open it. Each one tells you the likely cause and the exact next step. If a fix says "ask an admin," the precise sentence to send them is included.

Can't get in

Login problems

The login fields are greyed out, with a "not configured" banner

This is an admin/install issue, not yours: the platform's first-run config hasn't been written. You can't log in until it is. Send the admin to first-day setup — they either populate the required values and restart, or use the wrench icon on the login page to finish setup. Then reload.

The Register button is disabled

Your company runs HERD against its corporate directory (LDAP/AD), so self-registration is off. You don't need it — just sign in with your directory username and password; your account is created automatically on first login.

I was logged in, now everything errors / I get logged out

Your session token likely expired (30 minutes by default) and didn't refresh cleanly. Clear the site's local storage and log in fresh. If it keeps happening immediately after login, an admin may have rotated a key — everyone needs to re-login once after that.

Everything's empty

Inventory / palette shows nothing

Inventory says "No devices found"most common

Your user group hasn't been granted visibility to any device group yet. This is the number-one day-one confusion and it's a one-line admin fix.

Send your admin exactly this: "Can you add my user group to the device group(s) for the gear I need?" Then reload. (Admins: setup step 5.)

Less commonly: every device you can see is currently reserved and the palette's Show reserved resources toggle is off — flip it on.

The Inventory list has devices but the topology palette is empty

By design: the palette only shows DUTs (Management-type devices). If everything you can see is infrastructure switches, the palette stays empty — switches are wired in automatically by the routing system, not dragged by hand.

Reservation won't go through

Errors when booking

"Time conflict: devices already reserved"

An exclusive device you picked is already held during your window. Three options: pick a different window (the calendar shows the gaps), cancel the conflicting booking if it's yours, or swap in a different device. A device someone is mid-booking also counts as a conflict until they finish.

"The following devices are not available"

A device's status doesn't allow it. Exclusive devices must be AVAILABLE; if one shows RESERVED it's held elsewhere. OFFLINE or MAINTENANCE means an admin took it down on purpose — ask them if it shouldn't be.

"All devices must share the same topology type"

You mixed PHYSICAL and CLOUD devices in one booking. Split it into two reservations, one per type.

My reservation shows FAILED

No devices were actually reserved — provisioning couldn't complete, and the row is kept only for audit. Just create a new reservation for the same devices and window; it usually succeeds on the retry once the backend is healthy. If it fails repeatedly, that's an admin-side service issue (an inventory or internal-token problem) — flag it.

Stuck in PENDING past its start time

The activation task runs about once a minute, so give it up to 60 seconds of drift. If it's been much longer than that, the task may have stalled — tell an admin to restart the reservations service.

A red topology edge

The edge won't go green

Red + "no path"

No physical route exists between the two DUTs through known switches. Either they're genuinely in isolated fabrics, or the switches/cabling between them aren't recorded in inventory. Ask an admin to verify the cabling (or do it yourself via Cabling things up). For deliberate cross-site links, an admin adds a virtual tunnel device cabled into both fabrics.

Red + "uncabled port"

The specific port you chose has no physical cable recorded. Delete that line and redraw it against a different port in the wiring dialog (a cabled port is tagged CABLED; an uncabled one is tagged no cable, both informational, but only a cabled port will resolve a real path), or ask an admin to record that cable. To change just one line, click its layer pill on the canvas to expand its own delete control; or, if it's bundled with other connections between the same pair, click the bundle's count badge to find and delete that one connection.

"Can't drop the device here"

You're trying to mix a PHYSICAL device with a CLOUD one. They can't share a topology — start a separate one for the other type.

AI weirdness

AI generation problems

There's no "Use AI" button

The feature is turned off on this deployment (no API key configured). Nothing you can do as a user — ask your admin if it should be enabled. (Admins: set the key and restart the AI service.)

"Inventory shifted during generation"

A device the AI wanted became unavailable between proposing and committing. Just regenerate — it'll plan against the current inventory.

My device configs came back "admin required"

Pushing configs to devices is admin-only. Your topology and reservation were still created fine — only the config step failed. Either untick "Apply device configs" at commit, or have an admin apply them separately.

There's no "AI Assistant" tab on my reservation

Two reasons it hides: AI isn't configured on this deployment (same switch as the Use AI button), or you don't own that reservation — the assistant only runs against reservations that are yours.

The assistant timed out or says it can't see a device

Timed out: a heavy question fanned out into too many lookups — ask something narrower or split it in two. "Can't see that device": it's bounded by your visibility on purpose; if you can't see the device in inventory, neither can the assistant. Same permissions fix as an empty inventory.

Health & config

Polling & config pushes

A device shows UNREACHABLE but I can reach it

The health poll logs in exactly the way a real run would. If it can't authenticate (wrong IP / login / password in the device fields), it reports UNREACHABLE even though you can reach the box by other means. Fix the field data. Note also that after repeated failures the poll interval stretches out, so the badge can lag a recovery by a cycle.

No health badge at all on a device

That device isn't opted into polling. Set a poll interval (minimum 30s) on the device or its template — see health monitoring. No interval, no badge.

"Dry-run not supported" when scheduling a config apply

The device's driver hasn't declared dry-run support, so HERD refuses to simulate against it rather than guess. Either apply for real (carefully), or have the driver author add dry-run support. Restoring an old config version is also blocked while an active or pending reservation references the topology.

Admin / driver issues

Setting things up

Driver upload fails with 422 or 409

422 = wrong file type or too big. Use a .zip or .tar.gz under 10 MB. 409 = the driver name is already taken; names are unique, pick another.

Can't delete a driver

A template still points at it — drivers are reference-counted. Remove or repoint the template first, then delete the driver.

A bulk import rejected some rows

Read the per-row reason in the report — usually a reference that didn't resolve ("template not found by name"). Imports resolve references by name, so import templates before devices and devices before topologies. A reject never aborts the batch; fix the named rows and re-run. Always dry-run first to preview the whole thing.

A user reports the bell never ticks up

Check in their Settings → Notifications that the in-app channel is on and the relevant event type is still checked. Reservation events go to the reservation owner; health events go to admins and anyone with an active reservation on the device. If they expect email or chat, those are separate opt-in channels — off until switched on. Deeper failures are NATS/consumer issues for ops.

Genuinely stuck?

When it really isn't you

If you've matched a symptom above and the fix didn't take, it's likely a backend/ops problem rather than something in the UI. Before escalating, gather the four things that make it a five-minute fix instead of a back-and-forth:

  1. The exact error message (and the HTTP status if it's an API error).
  2. Your role (user / admin / superadmin).
  3. What you were trying to do when it happened.
  4. Roughly when it happened, so logs can be matched.

Every backend service exposes live API docs at https://<your-host>/api/<service>/docs (admin login required for most endpoints) — handy for confirming whether a problem is the UI or the service behind it.
