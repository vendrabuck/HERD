Device health & configuration

Two things HERD does once your devices exist: it can poll them to tell you which ones are actually reachable, and it versions every config it pushes so you can see, diff, and roll back what changed. Neither is on by default — this page turns them on and explains what you'll see.

Both features lean on drivers — the Python packages that know how to log into your hardware (see first-day setup). Health polling uses a driver's login/status/logout sequence; config apply uses the driver's apply path. A device whose driver can't do these simply won't participate.

Is it alive?

Device health monitoring

Health monitoring asks each opted-in device, on a schedule, “are you reachable and healthy?” by running its driver's login → status → logout sequence. The result becomes a coloured badge on the device's detail page and, when it changes for the worse, a notification.

Opt a device in

Turning polling on

Polling is off until you set a poll interval. You can set it on a single device, or on a template so every device of that type inherits it.

Set Poll interval (seconds) on the device or its template

Open the device (or template) and set how often HERD should check it. The floor is 30 seconds — anything lower is rejected so a typo can't hammer your gear.

Leave it blank to opt out

No interval = no polling. Most labs poll a handful of always-on infrastructure devices and leave DUTs alone. Set it per-template for a whole class, or per-device for one-offs.

The scheduler picks it up automatically

No restart needed. The execution service runs each opted-in device on its own cadence from then on.

The colour code, again

Reading the health badge

The device detail page shows the latest snapshot plus when it was last checked. Four states:

  1. The health badge. One of four states (below). Only shown for devices that are opted in — no interval, no badge.
  2. Last checked. When the last poll ran and how often it repeats, so a stale badge is obvious.
BadgeMeans
HEALTHYLast poll logged in, read status, and logged out cleanly.
DEGRADEDReachable, but the driver reported something off — a partial or warning condition.
UNREACHABLEThe poll couldn't complete — login failed or the device didn't answer.
UNKNOWNNot yet polled, or polling was just turned on. A transient starting state.

When it stops answering

What happens when a device goes bad

  • It backs off, it doesn't spam. After a few consecutive failures (three by default) HERD slows that device's polling with exponential backoff and jitter, so one dead box doesn't flood the audit log with identical errors.
  • The right people get told, once. When a device crosses the failure threshold — or recovers — HERD sends an in-app notification to all admins and to anyone with an ACTIVE reservation on that device. Because the alert fires on the threshold crossing, a device that flaps below the threshold generates no noise.
  • Recovery is an event too. When a device comes back to zero failures, that transition also notifies, so you're not left wondering whether it's still down.

Health alerts land in the same bell as reservation notifications, and users can opt out of them per-event in notification settings. They're on by default for admins.

Every change, kept

Device configuration versions

Whenever a config is applied to a device — by hand, by a reservation, or by the AI assistant — HERD snapshots it as a numbered version. The device's detail page lists them newest-first: who applied it, when, and the result.

  1. Current. The version live on the device right now.
  2. Diff. Opens a unified diff between any version and the current one.
  3. Restore. Re-applies an older version as a new apply. (Blocked while an active reservation depends on the topology — same guard as topology restore.)

What changed

Diff & restore

The diff is a plain unified view — removed lines in red, added lines in green — so you can see precisely what one apply changed before you trust or revert it.

Pushing config on a schedule

Scheduled apply & dry run

Instead of applying a config by hand, you can schedule it to fire automatically when a linked reservation goes ACTIVE — so the lab is configured the moment it's yours.

  • Schedule against a reservation. Queue a config push tied to a reservation; it runs when that reservation activates.
  • Cancel while it's pending. The owner or an admin can call it off any time before it fires.
  • Dry-run first. A scheduled (or assistant-proposed) apply can run in dry-run mode — the driver simulates the push and records the exact commands it would have sent, without touching the device. You review those commands, then promote it to a real apply.
Per-command transcripts

When a driver opts in, each apply records a line-by-line transcript — every command, its response, how long it took, and whether it was real or simulated. That transcript is exactly what the AI assistant's confirm dialog shows you, and it doubles as an audit trail for any apply.

Dry-run needs a willing driver

A driver has to declare that it supports dry-run before HERD will simulate against it. Drivers that haven't opted in can't be dry-run — the schedule endpoint, the AI tool, and the execution sandbox all refuse rather than guess. If you author drivers, see the driver guide in the repo.

A device shows UNREACHABLE but I can reach it myself
  • Check the credentials/fields the driver uses to log in (IP, login, password). A health poll runs the same login a reservation would — if the poll can't authenticate, neither can a real run.
  • Mind the backoff. After repeated failures the poll interval stretches out, so the badge can lag a recovery by a cycle or two. It'll catch up on the next successful poll.
  • UNKNOWN that never changes usually means the driver's status method isn't returning a clear result. That's a driver issue, not a HERD one.
