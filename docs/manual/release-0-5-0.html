Release 0.5.0

The version this manual documents. 0.5.0 teaches HERD Layer 3 as something you declare: a Layer 3 switch node on the canvas carries its own routes, HERD validates them against the switch when you save, and drives them when the reservation activates. Around that, the first two drivers for real network operating systems ship with the product, the reservation assistant can read this manual instead of guessing, and a manual wiring retry can no longer collide with HERD's own background one.

The short version

What 0.5.0 is

0.4.0 made HERD accountable for what the hardware was used for. 0.5.0 makes it speak Layer 3: a Layer 3 switch node carries a route table you edit on the canvas or import from the switch's saved config, HERD refuses a route the switch cannot honour when you save, and execution drives the fork's routes ahead of anything in the device's own config version. A route can name a virtual router where the driver supports one, and a route's interface has to sit on a wired port unless the switch's config marks that interface logical.

Under the floor, HERD now ships two driver packages for real network operating systems, proven against a checked-in lab of those systems on every change; a driver must report a device's rejection of a command as a failure, so a refused change can never read as applied; and the two wiring retry channels claim a failed connection before touching the device, so a switch never receives the same command twice.

The contents

What shipped

01

Layer 3 routing intent

ADR 0014, end to end: declare routes on a Layer 3 switch node in the topology editor, import them from the switch's saved config, and HERD validates them against the switch when you save and drives them when the reservation activates, ahead of any routes in the device's config version. A route can name a virtual router (VRF) when the driver supports it, and a route's interface must sit on a wired port unless the switch's config marks it logical. Routing intent → Version diff →

02

Drivers for real network operating systems

HERD now ships two driver packages an admin can upload as they are, frr_l3 (FRRouting as a Layer 3 switch) and srl_l2 (Nokia SR Linux as a Layer 2 switch), both proven against a checked-in lab of the real operating systems on every change. A driver must now report a device's rejection of a command as a failure, so a refused change can never show as applied. Uploading a driver →

03

The assistant can read the manual

Two new read-only tools, Search docs and Read doc, let the reservation assistant consult this manual, any document folders the operator adds, and allowlisted web pages, and cite what it found instead of guessing. What the assistant can see →

04

Wiring retry cannot double-drive

A manual Retry and HERD's own background retry now claim a failed connection before touching the device, so a switch never receives the same command twice, and a stale retry can never resurrect a connection you released. The Retry toast gains a seventh outcome, "already retrying", for a row the background channel already had in hand. The Wiring tab →

05

Classify one reservation now

An admin can ask for a purpose suggestion for a single ended reservation without waiting for the background sweep or running the whole Classify history backfill. API only in this release. Purpose review →

06

Commit waits for the fork to load

In live editing the Commit to reservation button is disabled until the reservation's fork canvas has loaded, so a fast click can no longer save an empty version and fail the device-set update. Committing →

Also in this release

  • Non-admins now see only their own devices when a topology is validated or a path is found: a device outside your groups reports as missing, and a hidden switch on a path shows as a hidden hop.
  • A driver that declares supports_vrf receives the virtual router on route changes; a route naming a virtual router on any other driver is refused and shown in the Wiring tab, never silently dropped.
  • Seeding a stack with demo data moved to the seedtools command (python -m seedtools full); the old script and its shell wrappers are gone.
  • Nightly test failures now keep a screenshot, page, console log, and traceback per failed browser test.
  • Fixed: a wiring retry that finished after you released the connection no longer re-creates it as failed.

The architecture is unchanged from 0.1.0: twelve FastAPI services behind Traefik, one PostgreSQL schema and migration chain per service, NATS JetStream with transactional outboxes for events. The 0.1.0 architecture section still describes it.

What it was tested against

Quality bar

Measured at the tagged commit by the full make everything run:

  • 5,443 backend unit tests across the 13 suites plus the repo-root suite; backend line coverage 96.8% with every service at 95% or higher.
  • 1,378 frontend tests via vitest, 90.4% line coverage.
  • 12 OpenAPI contract snapshot suites.
  • 221 cross-service integration tests (211 run, the rest gated on LDAP mode or an AI provider).
  • 164 end-to-end browser tests, run twice: 128 on the unseeded stack (36 device-gated skips) and 160 again on the seeded stack with no unexpected skip allowed (4 exempt).
  • 41 live-LDAP tests against the checked-in infra/ldap-test directory, hard-required in the gate.
  • New this release: 28 driver tests against real FRRouting and Nokia SR Linux nodes in the checked-in lab, run on every pull request and inside the gate.
  • Seven Postgres-live suites against the gate database, hard-required: the LDAP sync reconciler, advisory locks, the outbox wake-on-write, the fork restore-versus-save race, the two-session fork port-claim race, the Layer 3 route key width, and the new two-channel wiring retry claim race.
  • Load: 20 simulated users for one minute, 665 requests, 0 failures, median 10 ms, p95 170 ms.

The release gate is unchanged: a clean full validation run (lint, format check, every unit suite with coverage, frontend build, contract snapshots, integration, end-to-end, and load, against a rebuilt ephemeral stack) at the tagged commit, plus the same branch-protection ruleset on main described on the 0.1.0 page. The ruleset also covers release/* branches.

The honest part

Known boundaries

These are limits of 0.5.0, not bugs. If you hit one, the answer is "not yet", not "file a ticket".

  • Network element provisioning (anchored VLANs) is a later phase. Elements are canvas objects today: they attach, save, validate, and diff, but nothing is provisioned from them.
  • Manual wiring retry is not exposed through the external API. The /api/v1 wiring-status passthrough is deliberately read-only; retrying a failed connection is an interactive, owner-gated action.
  • A failed VLAN removal is logged, not blocked on. If delete_vlan fails on last-free, the allocation is already released and the empty definition lingers on the switch until an operator removes it. Bounded lingering is the accepted trade.
  • AI recipe authoring is dark by default. Unchanged from 0.1.0: it stays behind AI_RECIPE_AUTHORING_ENABLED.
  • Driver packages are trusted code. Unchanged from 0.1.0: POSIX setrlimit caps and a subprocess boundary are resource bounding, not OS-level isolation.
  • Purpose classification is off by default. It needs a configured AI provider and AI_PURPOSE_CLASSIFICATION_ENABLED. A suggestion never writes the confirmed category by itself; an owner or an admin does.
  • Config-version history for a device outside your groups answers "Device not found". The same answer as the device page gives. That is the visibility rule catching up, not a missing device.
  • A route that names a virtual router needs a driver that declares it. Only a driver declaring supports_vrf drives one; on any other driver the route is refused as l3_vrf_unsupported and stays visible in the Wiring tab until the intent or the driver changes. The shipped frr_l3 driver declares it.
  • Classify now for a single reservation is an API call in this release. The Purpose review page has no button for it yet.
  • The assistant's web sources are off by default. They stay behind AI_DOCS_WEB_ENABLED and are limited to operator-allowlisted https prefixes; the built-in manual and any configured folders are on.

Some manual pages describe screens that only appear when a feature is configured, for example the AI Assistant tab, the Use AI button, the LDAP Sync page's actions, and the Purpose Review queue. On an install where the feature is off, those surfaces are hidden or inactive. That is the feature gate, not a broken deployment.
