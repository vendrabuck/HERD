Release 0.2.0

The version this manual documents. 0.2.0 finishes the connection-driven wiring story started in 0.1.0, hardens the paths that guard live wiring, and closes the admin UI gaps 0.1.0 listed as known boundaries.

The short version

What 0.2.0 is

0.1.0 built the platform. 0.2.0 finishes its hardest promise: that the wiring a reservation holds on real switches always converges to the wiring its topology says it should hold. Initial provisioning, live fork saves, and terminal teardown now all flow through one connection-driven reconcile pipeline at L1, L2, and L3, and the release removes the legacy provisioning code that pipeline replaces.

Around that core, 0.2.0 hardens the failure paths that touch live wiring, gives HERD ownership of the switch-side VLAN definition lifecycle, tightens two access-control gaps, and ships the two admin surfaces 0.1.0 shipped without: ACL grants management and dynamic template authoring.

It lands 30 merged changes in the week after 0.1.0.

The contents

What shipped

01

One reconcile pipeline for all wiring

The connection-driven reconcile epic is complete. Activation, fork saves, and teardown all reconcile the switches against the reservation's saved intended wiring through the same full-reconcile pipeline over per-connection ledgers, at all three layers. Adding or removing devices on an ACTIVE reservation wires and releases only through fork saves, and the legacy device-set provisioning paths are retired outright. Live editing →

02

Wiring status across all three layers

Every row in a reservation's wiring status now carries its layer: L1 cross-connects, L2 memberships with the resolved fabric VLAN id, and L3 rows with a route count. The Wiring tab renders all three with direction-aware retry across the full six-outcome vocabulary, and the external /api/v1 facade gains a read-only wiring-status passthrough for automation.

03

HERD-owned VLAN definitions

The platform now owns the switch-side VLAN definition, not just membership. A fabric allocation's first built membership defines the VLAN on every switch the path transits, trunk-transit switches included; the last release removes it, guarded against a concurrent reuse of the same VLAN id. Driver create_vlan is required to be idempotent, and the requirement is documented in the driver contract.

04

Failure paths that cannot eat wiring

If the reconciler cannot read a reservation's intended wiring, it defers and retries rather than treating the failure as an empty set and tearing down live wiring. Terminal teardown freezes a reservation's wiring first, with commit-time frozen re-checks in all three ledgers, so a racing retry can never rebuild wiring on an ended reservation. Removing a device releases wiring from the last saved topology, never the unsaved draft, backed by a durable retry marker.

05

Upgrades that cannot drop events

A schema managed by migrations is never touched at boot, and the event consumers now wait for schema readiness instead of draining events into the dead-letter queue during the upgrade window between recreating containers and running migrations. Once migrations land, a waiting consumer starts on its own, no restart needed.

06

Admin surfaces for ACLs and dynamic templates

Two 0.1.0 boundaries close. Resource-level ACL grants get a management UI, so admins no longer drive the ACL API directly. The template editor gains dynamic template authoring and hypervisor registration, so hypervisor-backed resources can be defined end to end from the browser. Equipment administration →

Also in this release

  • Access-control tightening: bulk topology import updates enforce the creator-or-admin gate per row, and device-visibility lookups are self-or-admin.
  • A Playwright end-to-end suite that asserts backend-observable effects through API read-back after each UI action, not just UI acknowledgment.
  • The validation-gate stack runs in its own compose project, so a full-gate run no longer disturbs a developer stack on the same host.
  • A shared settings base class replaces eleven identical per-service configuration blocks.

The architecture is unchanged from 0.1.0: twelve FastAPI services behind Traefik, one PostgreSQL schema and migration chain per service, NATS JetStream with transactional outboxes for events. The 0.1.0 architecture section still describes it.

What it was tested against

Quality bar

  • Over 3,600 backend unit tests across the thirteen suites, on in-memory SQLite.
  • OpenAPI contract snapshot tests that fail on any public-API shape change.
  • 184 cross-service integration tests against a live stack.
  • 151 end-to-end browser tests: 122 Selenium, 29 Playwright.
  • Around 580 frontend tests via vitest, plus Locust load tests. Coverage targets 85% or higher per backend service.

The release gate is unchanged: a clean full validation run (lint, format check, every unit suite with coverage, frontend build, contract snapshots, integration, end-to-end, and load, against a rebuilt ephemeral stack) at the tagged commit, plus the same branch-protection ruleset on main described on the 0.1.0 page. The ruleset also covers release/* branches.

The honest part

Known boundaries

These are limits of 0.2.0, not bugs. If you hit one, the answer is "not yet", not "file a ticket".

  • Dynamic resources are authorable, not yet fully drawable. Dynamic templates can be created in the UI and booked, but the topology canvas has no affordance for placing them and the reservation detail modal does not yet list a reservation's dynamic requests. Both are tracked.
  • Manual wiring retry is not exposed through the external API. The /api/v1 wiring-status passthrough is deliberately read-only; retrying a failed connection is an interactive, owner-gated action.
  • A failed VLAN removal is logged, not blocked on. If delete_vlan fails on last-free, the allocation is already released and the empty definition lingers on the switch until an operator removes it. Bounded lingering is the accepted trade.
  • AI recipe authoring is dark by default. Unchanged from 0.1.0: it stays behind AI_RECIPE_AUTHORING_ENABLED.
  • Driver packages are trusted code. Unchanged from 0.1.0: POSIX setrlimit caps and a subprocess boundary are resource bounding, not OS-level isolation.

Some manual pages describe screens that only appear when a feature is configured, for example the AI Assistant tab and the Use AI button. On an install with no LLM provider configured, those surfaces are hidden and the AI endpoints return 503. That is the feature gate, not a broken deployment.
