# Development guide

This file collects the developer-workflow rules for HERD: how to install, run, build, lint, migrate, and gate the stack, how the validation pipelines and CI behave, the git, worktree, Dependabot, and release procedures, and the shared conventions every service follows. Rules about writing and running tests live in [TESTING.md](TESTING.md). Product behavior is documented in `docs/ARCHITECTURE.md` and `docs/specs/<area>.md`. The `Makefile` is the canonical command surface; a bare `make` prints the annotated target list. Backend uses `uv`, frontend uses `npm`. Delivery history for every feature lives in `CHANGELOG.md`; this guide records only the operative rules.

## Install and run

- `make install` installs Python deps (`uv sync --all-extras`); `make frontend-install` runs `cd frontend && npm install` (local frontend dev needs Node.js 22+).
- GOTCHA: after pulling a merge that touches `frontend/package.json`, an EXISTING checkout's `node_modules` is stale and the failure looks like broken code, not a stale install. Run `make frontend-install` (or `cd frontend && npm ci`) after such a pull; a fresh clone is unaffected.
- `make up` (alias `make dev`) starts the full stack in dev mode (hot-reload, volume mounts); `make prod` runs without reload; `make down` stops it; `make logs` tails all services.
- `make build` rebuilds all service images (`docker compose build`); `make restart` restarts all running services.
- `make frontend-dev` runs the Vite dev server at <http://localhost:5173>.
- Hot-reload does not cover every service: a service without a dev mount (`ai-orchestrator`, `notifications`, `acl`, `user-profile`) needs `docker compose up -d --build <svc>`, not a restart. An `herd_common` edit hot-reloads only in services that have a dev mount; the four rebuild-only services need the rebuild for it too.
- A fresh clone needs compose-time values in `.env` before the first `make up`: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `AUTH_SECRET_KEY`, `INTERNAL_API_TOKEN` (no compose defaults; interpolation fails or containers misbehave without them). `FRESH_SETUP.md` is the walkthrough. Rotating `INTERNAL_API_TOKEN` means restarting EVERY service: service-to-service calls 403 until both sides hold the new value.
- The `secrets` service refuses to boot without a valid `SECRETS_KEK` (base64 32 bytes) by design, so `make prod` requires it in `.env`; the dev/test override supplies a dev-only key, so `make up` and the ephemeral stack need no setup. A secrets container crash-looping at boot means key material, not code (see `docs/TROUBLESHOOTING.md`).
- The ephemeral stack is booted via `docker compose up` (no `-f`), so `docker-compose.override.yml` applies; `make prod` uses `-f docker-compose.yml` and excludes it. `make everything` and the ephemeral stack need `AUTH_METHOD=local` in `.env` (there is no LDAP server in the test stack; a stale `AUTH_METHOD=ldap` is the usual cause of a make-everything crash at stack boot. The gates' `_gate-ldap-tests` phase is unrelated: it runs host-side pytest against the standalone `infra/ldap-test` container, not the stack).
- Docker Compose 2.27.1 or later is REQUIRED (see Traefik below).

### Frontend toolchain floor (issue #885)

`frontend/package.json` declares `engines` `{node >=22, npm >=11.11.0}` and `frontend/.npmrc` sets `engine-strict=true`, so an older npm REFUSES `npm ci`/`npm install` with `EBADENGINE` instead of silently stripping the `libc` arrays Dependabot's npm (11.17.0) writes into `package-lock.json` (npm writes `libc` only since 11.11.0). engine-strict binds EVERY dependency's engines floor too: jsdom@30 needs Node >=22.22.2, so a host on an older Node refuses as well; fix the host (`nvm install 22`, `npm install -g npm@11.17.0`), never edit the committed `.npmrc` (one-off escape hatch: `npm_config_engine_strict=false`). ci.yml's frontend job installs npm@11.17.0 before `npm ci` and ends with `npm install && git diff --exit-code -- package-lock.json`, the frontend twin of `uv lock --check`. `frontend/Dockerfile` is unaffected only because its pre-install `COPY` names `package.json` and the lockfile and not `.npmrc` (do not fold `.npmrc` in or move `COPY . .` ahead of the install). `tests/unit/test_frontend_npm_engine_gate.py` pins all of this.

### Build identifier (issue #846)

`make version` prints the build identifier every image is stamped with. The Makefile computes and EXPORTS `HERD_BUILD` (`git describe --tags --always --dirty`: the tag alone at a release commit, else `vX.Y.Z-N-g<hash>`, N being commits since the tag) and `HERD_BUILD_DATE` (the HEAD COMMIT date in UTC, deliberately not the wall clock, which would change every image ID and recreate all 13 containers on every `make up`); an already-exported value wins. They reach images as build args declared as LATE as possible in every Dockerfile: in the stage that ships, each declared once, with NO `RUN`, `COPY`, or `ADD` after them, so every install is ahead of them under any spelling, and one `ENV` line after both. This is pinned by `tests/unit/test_build_args_wiring.py`, which since #1158 reads each Dockerfile as instructions per build stage. A `RUN` that needs the value after the `ARG` fails the guard by design: the `ENV` line already puts the value in the image. The frontend lines are judged in the stage that runs `npm run build`, and the frontend gets them as `VITE_HERD_BUILD`/`VITE_HERD_BUILD_DATE`. A bare `docker compose build` outside the Makefile, and every CI-built image, reports `dev`; a shallow clone without tags reports a bare hash.

### Gateway bind (issue #1256)

`docker-compose.yml` publishes Traefik's 80 and 443 on `${HERD_GATEWAY_BIND:-0.0.0.0}` (unset means every IPv4 interface; the dashboard stays on 127.0.0.1). The Makefile reads the same knob (environment or command line first, else the last `HERD_GATEWAY_BIND=` line of `.env`) into `GATEWAY_HOST` (`localhost` for unset, empty, or `0.0.0.0`, else the value as written) and EXPORTS `HERD_BASE_URL` (`https://<host>/api`) and `E2E_HOST_BASE_URL` (`https://<host>`) as defaults for every stack-addressing harness (seedtools, integration, contract, Playwright, the NOS lab via-stack suites, locust, whose `--host` drops the `/api`); `make gateway-url` prints the derived URL; the ports guard's messages name it. `make certs` names the bound address in the gateway certificate's SANs (issue #1239, below); browsers warn until that self-signed certificate is trusted by hand, and the harnesses skip verification. `tests/unit/test_compose_ports.py` and `test_gateway_ports_guard.py` pin the knob, the derivation, and the messages.

## Seeding

- `make seed` seeds a running stack with demo users, drivers, devices, cabling, groups, and topologies via `uv run python -m seedtools full` (subcommands `full`, `acl`, `frr`, `nos`, the latter two with `--full`); it is re-runnable (skips existing resources) and resolves credentials once, in `seedtools/client.py`: `SEED_*`, else `SUPERADMIN_*` from the environment, else the repo-root `.env`, else `admin@example.com`. `make seed-frr` and `make seed-nos` run the `frr` and `nos` subcommands.
- `make seed-frr` (`python -m seedtools frr`) layers the FRR live-config demo on top (the netmiko `frr_mgmt` driver plus the two lab routers; `SEED_FRR=1` on `full` does the same); idempotent, but live config (not dry-run) needs the external network-simulator lab reachable.

## Lint and format

- `make lint` runs `uv run ruff check` over `services/` plus the repo-root scripts in the Makefile's `ROOT_PY` list (currently `seedtools/`, `scripts/check_image_matches_lock.py`, `tests/ai_eval/`, and `tests/unit/`), and `cd frontend && npx eslint src --max-warnings 0`.
- `make format` runs `uv run ruff format` then `uv run ruff check --fix` over the same Python paths.
- CI lints the same paths with `ruff format --check` (no mutation), so run `make format` before pushing; a new tracked repo-root Python script must be added to `ROOT_PY` and the CI lint lines or it goes unlinted.
- `make audit` runs `pip-audit` (Python) and `npm audit` (frontend) for known-vulnerability scanning; set `AUDIT_STRICT=1` to make it fail on findings.
- ruff config (root `pyproject.toml`): line length 100, lint rules `E`, `F`, `I`. Frontend eslint runs with `--max-warnings 0`, so warnings break the build.

## Migrations and shells

- `make migrate` runs Alembic on all DB services; `make migrate-<svc>` for one. `make shell-<svc>` opens a bash shell in a service container.
- `config` has no database, so it has no `migrate-config` or `shell-config` target. `ai-orchestrator` does have a database (its `ai_orchestrator` schema), so `make migrate-ai-orchestrator` and `make shell-ai-orchestrator` are valid. The `common` service ships its code under `herd_common/`, not `app/`, and has no service container.
- A schema change means adding an Alembic revision under `services/<svc>/migrations/versions/`; `make migrate-<svc>` runs only that service's upgrade. The Postgres schemas themselves are created by `infra/postgres/init.sql`, mounted as the Postgres entrypoint init script, so it runs only on a fresh data volume: a NEW service must add its `CREATE SCHEMA` line there, and an existing stack will not pick that up without recreating the postgres volume (this bit the `integration` and `secrets` service scaffolds).

### Migration lifecycle

`herd_common.schema_init.create_all_and_stamp` runs `metadata.create_all` only on a fresh schema (then stamps head) or a legacy unstamped one; a schema with an `alembic_version` stamp SKIPS create_all entirely and evolves only through Alembic. Bare `op.create_table` migrations are therefore safe on upgraded-in-place stacks, and a per-migration `has_table` guard is no longer required for new migrations. On the stamped path, startup logs advisory-only drift warnings (stamped behind head: run `make migrate`; at head with model tables missing; stamped-but-empty schema; stamp from a newer build after an image rollback); none of them block boot. `docs/OPERATIONS.md` has the upgrade order (build, recreate containers onto the new images, THEN `make migrate`; `make migrate` execs into the running container, so migrating before the recreate runs the old image's migration files). (issue #419)

### Startup must survive a schema one migration behind (issue #1261)

The "boots and warns" promise above holds only if nothing a service runs at startup reads a column the previous release's stamped schema lacks. Auth's `_seed_superadmin` once did `select(User)` and a column-adding release (0009) could not boot until `make migrate-auth`, which works under `make up` only because the dev reloader keeps the crashed container alive for the exec (under `make prod` the container crash-loops; the remedy is `docker compose -f docker-compose.yml run --rm <svc> alembic upgrade head`). Now every startup existence check selects ids only (`superadmin_exists`, `email_registered`, `group_name_exists`), pinned by `services/auth/tests/test_startup_seed_schema.py` (statement recording plus a users table of the previous shape) and spec rule IAM-BOOT-6. A NEW startup read in any service must select only the columns it needs; proven live by downgrading a running stack's schema one revision and restarting the service (healthy, advisory warning only).

## Validation pipelines (the gates)

- `make master-quick`: fast gate (`uv lock --check`, then dep sync, `make format`, lint, unit, frontend tests + build, image build). The lock check runs first because `uv sync` without `--locked` rewrites a stale uv.lock in place, which would repair the drift CI fails on (PR #1207). Note it runs `make format`, so it can mutate the working tree; CI's `ruff format --check` does not.
- `make master`: adds the live-LDAP phase (`_gate-ldap-tests`: boots `infra/ldap-test` if not already up, runs `test-auth-ldap` hard-required, tears the LDAP container down only if this run started it) plus an ephemeral stack for contract + integration + e2e, then (issue #572) two more phases after e2e: `_gate-ldap-stack-tests` connects `ldap-test` to the gate network, recreates ONLY the gate's `auth` container in LDAP mode (`--no-deps --force-recreate` with a scoped `AUTH_METHOD=ldap` env override), runs `tests/integration/test_ldap_auth.py` plus `test_ldap_sync_admin.py` with `HERD_INTEGRATION_LDAP=1`, and ALWAYS (trap) restores auth to local mode; then `_gate-pg-live-tests` runs every `services/*/tests/*_live_pg.py` suite (fifteen today, tabled in [TESTING.md](TESTING.md)) hard-required (`HERD_TEST_PG_REQUIRED=1`) against the gate Postgres on host port 5433. Both recipes are deliberately `$(MAKE)`-free so `make -n` on either stays a dry run; `master` and `everything` themselves are not (their recipes hold `$(MAKE)` lines), so never `make -n` a gate.
- INCIDENT RULE: `LDAP_COMPOSE` is pinned with `-p herd-ldap-test`; an exported `COMPOSE_PROJECT_NAME` otherwise overrides a compose file's `name:`. Every secondary compose file gets an explicit `-p`; never `--remove-orphans` on a single-service file unless the call pins that file's own project with `-p` (`ldap-down` and `ldap-reset` do, safely).
- `make master-clean`: removes this checkout's dev and gate compose images (selected by the `com.docker.compose.project` label, so the test labs' and other checkouts' images are kept), then runs `master` with both builds no-cache: `BUILD_NO_CACHE=1` for master-quick's dev-project build and `GATE_NO_CACHE=1`, which makes `_master-stack-up` run `$(GATE_COMPOSE) build --no-cache` before its `up -d --build` (PR #1207).
- `make everything`: adds `uv lock --check` before `uv sync`, coverage, format-check (with `ROOT_PY` parity), the same live-LDAP phase, the NOS lab dialect tier (`nos-test-dialect`) as its own phase right after it, a second frontend run under `TZ=America/Los_Angeles` (`test-frontend-tz`), the package-lock.json sync check after the frontend build, the image-versus-lock check on the freshly built ai-orchestrator image (`check-image-lock`, after `docker compose build`, no stack needed), the two post-e2e LDAP-mode/Postgres-live phases, and load tests. `tests/unit/test_gate_ci_parity_wiring.py` pins the four CI checks (and master-quick's lock check) by reading ci.yml's own commands; its first vitest run (coverage-frontend) runs under the host's zone, so on a non-UTC host neither run is UTC. Every gate builds the image set twice (the dev-project `docker compose build`, whose `<dir>-<svc>` images the gate never runs, then the gate's own `up --build`, mostly layer-cache hits); dropping the first is an open owner decision. `ROOT_PY` is the list under Lint and format above.
- `make everything-noload` (or `EVERYTHING_LOAD=0`) skips only the load-test tail; after the gate seed, a second e2e pass, `make test-e2e-seeded` (issue #629), runs before the load-test tail; the gate seed and `test-e2e-stop` still run.
- A SUCCESSFUL run seeds the gate stack and LEAVES IT RUNNING at <https://localhost> (no re-seeding needed to use it); `make gate-down` stops and purges it, then `make up` restores the dev stack. While it runs, `make up` refuses to start the dev stack (the gateway ports guard below), and the closing banner says so. Both gates also refuse to START their stack while another checkout's stack holds 80/443 (`_assert-gate-ports-free`). A failed run still tears the gate stack down via the trap (a failure before the stack phase never started one). Every gate run, pass or fail, leaves the dev stack STOPPED (gate-clean stops it first); `make up` restores it.
- RUN THE GATE DETACHED: a `make everything` started from a Claude session dies with the session (SIGTERM, `Error 143` at whatever phase it was in, the trap tears the stack down). Start it as `setsid make everything > <log> 2>&1 < /dev/null &` and watch the pid; the run then survives a restart and the log carries the result.

### Gate isolation

The master/everything ephemeral stack runs in its OWN compose project (`<dir>-gate`, e.g. `herd-public-gate`), so gate runs no longer destroy the dev stack's volumes or seed; `gate-clean` stops the dev stack WITHOUT `-v` (the projects share host ports, so it must stop) and purges only the gate project. `make clean` KEEPS volumes; the destructive variant is `make clean-data`. `make clean`'s cache purge prunes `./.claude` (agent worktrees there are other checkouts), using `-exec rm` because `-delete` implies `-depth`, which turns `-prune` off. Gate-phase `test-integration`/`test-e2e` sub-makes pass `COMPOSE_PROJECT_NAME=<gate project>` so bare `docker compose` calls in recipes AND in test code (the outbox outage test, the config e2e exec) follow the gate project; standalone runs still target the dev stack.

Live-gate note for worktree stacks: `.env` AND `spark-ca.pem` are untracked and do not propagate to worktrees; copy BOTH into a worktree before `docker compose up` there, or the compose bind-mount turns the missing CA file into a Docker-created directory and the AI client 503s with IsADirectoryError. Remove the copies before staging anything.

## Gateway, ports guard, and Traefik

- Traefik v3 terminates TLS and routes `/api/<service>/...` path prefixes. Its static configuration is the `traefik` command list in `docker-compose.yml` (PR #1240); only the dynamic config and the TLS certs live under `infra/traefik/`. GATEWAY CERTIFICATE (issue #1239): no certificate or key is tracked (only `infra/traefik/certs/README.md`, which keeps the directory in every clone so Docker never creates it as root). `make certs` (`scripts/make_certs.sh`) writes `server.key` (RSA 2048, 0600) and `server-chain.crt` (self-signed, 3650 days, `CA:FALSE`, `serverAuth`; SANs `DNS:localhost`, `IP:127.0.0.1`, `IP:<HERD_GATEWAY_BIND>` unless unset or `0.0.0.0`, then each `CERT_SANS` entry, duplicates dropped) when the key is ABSENT; with both files present it prints one line and runs no openssl; with the key present and the certificate missing it issues a certificate for the existing key, never rewriting it; `CERT_FORCE=1` regenerates both and says so. `dev`, `prod` (so `up`), and the gate's `_master-stack-up` depend on it, after their ports guard, so a fresh clone is served the generated certificate by construction; CI and nightly start their stacks with bare `docker compose up -d` and still get Traefik's default certificate (their harnesses skip verification). `dynamic.yml` lists the pair under `tls.certificates` AND `tls.stores.default.defaultCertificate`, because a client without SNI (every client by IP address, and OpenSSL 3.0 `s_client` without `-servername`) is otherwise served `TRAEFIK DEFAULT CERT`. A running Traefik picks up a new pair only when recreated. Trusting it is manual (FRESH_SETUP.md step 3). `tests/unit/test_make_certs_wiring.py` pins the wiring, both `dynamic.yml` entries, and the generated files through real `make` in scratch checkouts.
- Each stack's Traefik discovers only its own project's containers (PR #1240): its whole static configuration is the `traefik` command list in `docker-compose.yml` (there is no `traefik.yml` file under `infra/traefik/`; Traefik's file, flags, and env sources are mutually exclusive and a file wins, so a flag beside `--configFile` is ignored, which had left the dev override's `--log.level=DEBUG` inert), carrying `--providers.docker.constraints=Label(`com.docker.compose.project`,`${COMPOSE_PROJECT_NAME:?...}`)` and `--providers.docker.network=${COMPOSE_PROJECT_NAME:?...}_herd-net`. Docker Compose 2.27.1 or later is REQUIRED: only since then does compose always set `COMPOSE_PROJECT_NAME` for interpolation (from `-p`, the environment, `.env`, or the directory; compose-go #628), and the `:?` message refuses to render rather than match no container. Never add a traefik `command` to an override (it REPLACES the base list, constraint included), and never export `COMPOSE_PROJECT_NAME` from the Makefile for this. The `network` flag does not filter; the constraint is what isolates. A route listing servers from two stacks (`curl -s http://127.0.0.1:8080/api/http/services`) means a Traefik predating #1240.
- RESTART RULE: RECREATE, never restart, a Traefik created before #1240 (`docker compose up -d`, or `-p <project> up -d --no-deps --force-recreate traefik`): it still bind-mounts the deleted `traefik.yml`, and a restart (`docker compose restart`, a daemon restart, a reboot under `unless-stopped`) makes Docker create a root-owned DIRECTORY in its place (`traefik.yml` under `infra/traefik/`) and the start fails with `not a directory`; `sudo rmdir infra/traefik/traefik.yml` removes it. `make restart` recreates such a Traefik itself before `docker compose restart`.
- The gate's `_master-stack-up` depends on `_assert-gate-ports-free` (`HERD_GATE_PROJECT="$(GATE_PROJECT)" sh scripts/check_gateway_ports_free.sh "$(GATE_PROJECT)" "rerun the gate"`; `$(MAKE)`-, `exit`-, and `exec`-free): by then `gate-clean` has stopped this checkout's dev stack and purged its stale gate, so only a FOREIGN stack trips it, and without it the gate's seed, integration, and e2e phases (all addressed to https://localhost) would write into that other, serving stack. `tests/unit/test_gateway_ports_guard.py` pins the script, the Makefile wiring (real make in scratch checkouts named `HERD_Public` and `HERD.v2`, `DOCKER_HOST` on a dead socket), `make restart`, and the exact Traefik flag list.

### Dev and gate stacks share ports 80/443 (2026-10-28, PR #1240)

The dev stack and the gate stack a successful `make everything` leaves serving the gateway publish the same host ports 80/443, so they never run together. `make up`, `make dev`, and `make prod` depend on `_assert-gateway-ports-free`, which runs `scripts/check_gateway_ports_free.sh` with the project name docker compose ITSELF reports (`COMPOSE_OWN_PROJECT_CMD`: `docker compose config 2>/dev/null | sed -n 's/^name: //p' | head -n 1`), never `DEV_PROJECT`, because compose keeps `_` and drops `.` and spaces where DEV_PROJECT maps them to `-`, and compose reads `COMPOSE_PROJECT_NAME` from `.env`, which make never does; an empty answer fails closed (exit 2, `Could not determine this checkout's compose project name`). It REFUSES while any container of another compose project publishes host port 80 or 443 (`docker ps --filter publish=<port>` matches the HOST port), naming the holder with its `com.docker.compose.project.working_dir`. A holder named exactly this checkout's `$(GATE_PROJECT)` (passed as `HERD_GATE_PROJECT`) is "this checkout's gate" with the two remedies (use it, or `make gate-down`, which purges the gate volumes; it may be serving as the demo, confirm first); any other `*-gate` holder gets the exact teardown `docker compose -p <holder> --profile e2e down -v --remove-orphans`. The script reads `<project>|<name>|<working dir>` with `IFS='|'` on purpose (a tab is IFS white space and `read` collapses an empty project field). Only 80 and 443 are checked, by design. `make logs` prints a one-line note through the script's `--list` mode when the dev project has no containers but another project holds 80 or 443.

Before the guard, the symptom was `dependency ... is unhealthy` with service logs ending in `socket.gaierror: Temporary failure in name resolution`: dev Traefik stuck in `Created` and, after a retried `make up`, dev `postgres-1`/`nats-1` re-started with NO network attached (`docker inspect <c> -f '{{json .NetworkSettings.Networks}}'` prints `{}`). If that state is already on the host: `make gate-down` if the gate holds the ports, `docker compose down` (keeps dev volumes), then `make up`; diagnose with `docker network inspect herd-public_herd-net` and `getent hosts postgres` inside a service container before touching anything. The guard sees Docker containers only, never a host process on 80/443; CI and nightly start their stacks with bare `docker compose up -d`, so the dev guard never runs there.

## DLQ inspection

DLQ commands run through `natsio/nats-box:0.14.5` on `<project>_herd-net` (`nats:2.10-alpine` has no CLI). Inspection is read-only (`stream info`, `stream subjects`, `stream get`) and creates no consumer; purge needs `--force`. The guard `tests/unit/test_docs_nats_cli_form.py` is described in [TESTING.md](TESTING.md).

## Git, GitHub, and worktree gotchas

- The code-review skill run by a reviewer agent can leave the main checkout on a `pr<N>-review` branch; confirm `git rev-parse --abbrev-ref HEAD` is main before pulling.
- Worktrees carry NO `.gitignore` (it is untracked in the main checkout), so the frontend's `node_modules` and `dist` directories and a copied `.env` all show as untracked there; stage by name only, never `git add -A` in a worktree, and remove any copied `.env`/`spark-ca.pem` before staging.
- A PR body line "Fixes #A and #B" auto-closes only #A; write "Fixes #A. Fixes #B." on separate lines or close by hand.
- Never chain `git rebase` with `git push` in one command: a conflict stops the rebase but the push still goes out with the OLD branch tip.
- `gh pr checks <N> --watch` exits 0 even when an ADVISORY job (integration, nos-dialect) failed, because only required checks drive its exit code. The merge gate is a direct count of non-passing checks (`gh pr checks <N> | awk -F'\t' '$2!="pass"' | wc -l` must print 0), never the watch's exit status.
- `gh pr merge --match-head-commit` takes the FULL 40-character SHA; a short SHA is a GraphQL coercion error and the PR stays open (2026-10-12).
- A CodeQL alert is dismissed through `gh api -X PATCH repos/vendrabuck/HERD/code-scanning/alerts/<n> -f state=dismissed -f "dismissed_reason=false positive" -f dismissed_comment=<at most 280 characters>` (reasons are spelled as the UI shows them, not `false_positive`), then `gh run rerun <id>` of the PR's CodeQL run so the results check recomputes; a sink a PR MOVES is reported as a NEW alert on the PR and the old one on main closes as fixed on main's next scan (alerts 32 and 33 for #1183).
- Never call a remote branch stale from a truncated listing: `gh pr list` defaults to 30 rows and any `--limit` cuts more. Before advising a branch deletion, run `gh pr list --state open --head <branch>` for that branch.
- `git branch -r` shows the LOCAL remote-tracking refs, which keep every branch the remote has already deleted until `git fetch --prune`; judge staleness from `git ls-remote --heads origin`. The repo has delete-branch-on-merge ON, so `git push origin --delete <branch>` right after `gh pr merge` prints "failed to push some refs"; an empty `git ls-remote --heads origin <branch>` is the proof of deletion.
- Merge policy (standing): a reviewed PR may be merged once ALL checks are green (never on red or pending); after merging, delete the remote branch and verify the deletion with `git ls-remote`.

## CI, nightly, and CodeQL

- CI (`.github/workflows/ci.yml`) runs four jobs: `backend` (`uv lock --check`, then `ruff check`, `ruff format --check`, the image-versus-lock guard described under Dependabot below, then `make -j4 -Otarget coverage-parallel COV_XML=1`), `frontend` (lint/test/build), an advisory `integration` job (boots the stack, runs contract + integration), and an advisory `nos-dialect` job (`make nos-test-dialect` against the lab). A scheduled `nightly.yml` runs the heavy suites (contract, integration, e2e, seed + locust load) that PR CI skips. A failed integration run still uploads the compose logs (`_collect-stack-diagnostics`).
- CodeQL runs from `.github/workflows/codeql.yml` (advanced setup; actions + javascript-typescript + python, PRs to main, main pushes, weekly cron): GitHub's default setup was DISABLED and must stay disabled or the workflow's SARIF uploads are rejected.
- Promoting `nos-dialect` to a required check is a ruleset change.

## Dependabot

Dependabot's pip-ecosystem PRs bump `pyproject.toml` specifiers but never regenerate `uv.lock`. The backend job's `uv lock --check` step turns that drift into a red check on the Dependabot PR itself; the fix is always the same: regenerate the lock (`uv lock`) and push it to that PR's branch. When SEVERAL pip PRs are red at once, do not fix them one by one (each lock regeneration conflicts with the next): open ONE combined branch with all the specifier bumps and a single `uv lock`, then close the Dependabot PRs as superseded. If `ruff` is among them, run the newly locked ruff over the CI lint paths first (`uv tool run ruff@<version> check ...`), since a linter bump is the one that can fail CI by itself. Frontend PRs conflict on the lockfile after each merge: comment `@dependabot rebase`, never hand-resolve `package-lock.json`. Sibling lockfile PRs often stay CLEAN after one of them merges (their hunks do not touch), so they can merge in sequence, but a lockfile that merges without a textual conflict has proven nothing about resolving: wait for main's own CI on the merged result before merging the next batch (2026-10-28, 14 Dependabot PRs cleared this way, main's `uv lock --check` and the package-lock sync check green after each batch).

Since #593 the images are lock-faithful too: every service Dockerfile copies the workspace `pyproject.toml` and `uv.lock` under `/lock` (NOT `/app`, where the root pyproject collides with the service's package discovery) and installs from `uv export --frozen --package herd-<svc>`, then the editable installs with `--no-deps`; a stale lock fails the image build as well. CI's backend job builds the ai-orchestrator image and `scripts/check_image_matches_lock.py` diffs `pip list` inside it against the export (PEP 503 names, marker-aware; only the two editable packages and pip tolerated).

## Branch protection and releases

- The public repo enforces a branch-protection ruleset on `main` and `release/*`: a PR is required and the `backend` + `frontend` checks must pass before merge; force-push and deletion are blocked. There are no direct pushes to the default branch.
- Releases v0.1.0 through v0.6.0 are tagged (hashes and dates in CHANGELOG.md and `git tag`), each with a `release/X.Y.Z` branch at the tagged commit and a published GitHub Release; main is at 0.7.0.dev0 (frontend 0.7.0-dev); latest release v0.6.0 at 3216868f (2026-10-01; three security advisories published with it).
- Tag by explicit commit (`git tag -a vX.Y.Z <commit>`), never bare HEAD, and merge the next-dev bump PR only after the tag exists on the remote. The release PR merges BEFORE the gate run: the gate must run on the commit that gets tagged (a run on the pre-bump commit is a rehearsal; the About page skew e2e only sees a plain release version on the bumped commit), and nobody pulls into the main checkout while a gate run is active there. Images built during the gate predate the tag, so the gate stack's build string reads `v<previous>-N-g<hash>` until rebuilt.
- Each release also gets a manual page (`docs/manual/release-<X-Y-Z>.html`) plus the nav repoint across the other manual pages; `docs/MANUAL_UPDATE_BRIEF_0.3.0.md` is the worked example of the brief that drives that refresh (`docs/MANUAL_UPDATE_BRIEF_0.4.0.md`, `docs/MANUAL_UPDATE_BRIEF_0.5.0.md`, and `docs/MANUAL_UPDATE_BRIEF_0.6.0.md` also exist). The release gate is a clean `make everything` at the tagged commit. `CHANGELOG.md` (repo root) gets a section per release.
- After tagging, main bumps to the next `X.Y.Z.dev0` (PEP 440, all 13 workspace pyprojects) and the frontend to `X.Y.Z-dev` (semver), with `uv.lock` and `package-lock.json` regenerated in the same PR so the lockfile gates stay green.

## Compose settings wiring

Compose passes a variable to a service ONLY through an explicit `${VAR}` line in its `environment:` block, and no service uses `env_file`, so a knob listed in `.env.example` but missing from compose is inert in the container (issue #849). `tests/unit/test_compose_settings_wiring.py` (issue #873) enforces it for EVERY service: each Settings field is either passed through by base `docker-compose.yml` or listed in its `_EXEMPTIONS` with a reason (`db_schema`, `*_service_url`). Since #1158 passed through means the WHOLE value is exactly `${VAR}` or `${VAR:-default}` (default equal to the Settings default, pinned, except `cors_origins`, whose compose default differs by decision and is recorded in `_DEFAULT_MISMATCH_EXEMPTIONS`), where `VAR` is the field's own name upper-cased or the variable recorded for it in `_RENAMED_WIRING` (`SECRET_KEY`, `ALGORITHM`, auth's two token lifetimes; `DATABASE_URL` must interpolate its three `POSTGRES_*` variables). Another variable, text around the substitution, `$${VAR}`, `${VAR-x}`, `${VAR:?x}`, `${VAR:+x}`, and a bare `$VAR` are not wired; a new field wired under another variable name needs a `_RENAMED_WIRING` entry; stale exemptions fail, services are discovered from `services/*/app/config.py`, and an active `AI_*` key in `.env.example` must be set on ai-orchestrator's container key of the SAME name to exactly `${KEY}` or `${KEY:-default}` (interpolated under another key or inside a longer value no longer counts, #1181). A new setting needs the Settings field, the compose line (or an exemption), and a `docs/ENV_VARS.md` row; a new AI setting also needs `.env.example`. The config service has no `app/config.py`, so this guard does not cover its knobs; they are checked by hand.
