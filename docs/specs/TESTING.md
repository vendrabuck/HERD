## Running tests

- `make test` runs all 13 backend suites (the Makefile's `SERVICES` list: the 12 services plus `common`); `make test-<svc>` runs one (for example `make test-auth`, `make test-inventory`), EXCEPT the `integration` service's unit suite, which is `make test-integration-service` (`make test-integration` is the cross-service suite against a running stack; the generated pattern target is filtered out to avoid the old silent shadowing).
- Run a single backend test by going into the service directory: `cd services/<svc> && uv run pytest tests/test_file.py::test_name -v`. Each service runs pytest from its own dir; the root `[tool.pytest.ini_options]` sets `asyncio_mode = "auto"` and `filterwarnings = ["error"]`, so any warning fails the test.
- Backend unit tests run against in-memory SQLite (aiosqlite) with no real DB and no migrations; integration and e2e tests need the Docker stack up.
- Integration, contract, e2e, and load tests REQUIRE a running stack: `make test-integration` (and `make test-integration-ai` for the model-dependent AI tests, below), `make test-contract`, `make test-e2e` (then `make test-e2e-stop`), `make test-load` (`make test-load-ui` for the locust web UI).
- A small repo-root `tests/unit/` suite covers the seed script, the checked-in drivers (the FRR driver plus the `mock_l1`/`mock_l2`/`mock_l3`/`mock_hypervisor` test drivers), and the contract suite's OpenAPI fetch-retry helper (the issue #199 flaky-fetch fix, exercised via `httpx.MockTransport`): `uv run pytest tests/unit/ -v` from the repo root, no stack needed. It is wired in via the `test-root` target, which `make test`, `make coverage`, and `make coverage-parallel` all depend on, so CI exercises it too.
- Contract tests snapshot each service's `/openapi.json` against `tests/contract/snapshots/<svc>.json`; after an intentional API-shape change, regenerate with `HERD_UPDATE_OPENAPI_SNAPSHOTS=1 make test-contract` (stack up) and commit the snapshot diff. The contract snapshots do NOT record query parameters, so a new list parameter leaves them unchanged; the v1 snapshot (`tests/contract/snapshots/v1.json`) records methods, paths, and component schemas only, so a parameter format change does not move it. `docs/api/v1-openapi.json` is updated by hand alongside facade changes, not regenerated by the contract suite, whose snapshot lives separately at `tests/contract/snapshots/v1.json`; an additive facade change should touch both.

## Coverage

- `make coverage` / `make coverage-frontend` produce coverage reports; `COV_XML=1` makes the backend targets write a repo-root `coverage-<svc>.xml`: `coverage` adds it beside its terminal report (it never writes HTML), and `coverage-<svc>` (hence `coverage-parallel`, which depends on them) writes it in place of its HTML report, keeping the terminal one; that file is how CI consumes them (`make -j4 -Otarget coverage-parallel COV_XML=1`); `coverage-frontend` ignores the flag.
- Since #658 `frontend/vite.config.ts` carries an include-based `test.coverage` block (`include: ["src/**/*.{ts,tsx}"]`, text + json-summary + html reporters, no thresholds), so a file never imported by any test shows at 0% instead of being absent from the report; `coverage-summary.json` in the generated `coverage` directory under `frontend/` is the machine-readable result.
- Coverage-gap triage: most backend ROUTER misses were not missing behavior but coverage.py under-attributing post-await lines in async handlers driven through `httpx.ASGITransport`. The repo convention is a direct handler-call test file (`test_routers_direct.py` in auth, cabling, secrets, acl, integration) with a real in-memory session; verify a miss is real before writing a test (one lane proved it with `sys.settrace`), because some misses ARE real (cabling prune paths, execution race branches, AppLayout's dropdown close). Frontend gaps were real; the remaining sub-85% files are listed in `docs/GAPS.md` and all predate v0.2.0.

## Frontend tests

- `make test-frontend` runs vitest; a single frontend test is `cd frontend && npx vitest run <path>`, watch mode is `npm run test:watch`.
- `make test-frontend-tz` runs the same suite under `TZ=America/Los_Angeles`, ci.yml's second run. `dateUtils.test.ts` passes under any TZ, and since #1185 CI's `frontend` job runs vitest twice, under the runner's UTC and under `TZ=America/Los_Angeles` (step `env:`, pinned by `tests/unit/test_ci_frontend_tz_wiring.py`, which requires a known non-UTC zone with daylight saving time and the same command as the UTC step).
- `make check-image-lock` runs the image-versus-lock check against the image this checkout's `docker compose build` tagged (name from `docker compose config --images`; one throwaway `docker run --rm`, no stack).
- The test runner is vitest 5 with `frontend/src/test/vitest-jest-dom.d.ts`, a TEMPORARY type shim that re-augments vitest 5's two-parameter `Assertion` with jest-dom's matchers (jest-dom 7.0.1's one-parameter augmentation no longer merges; upstream testing-library/jest-dom#738). Delete the shim once jest-dom ships a vitest 5 compatible release; runtime was never affected.
- GOTCHA: jsdom misses browser-only bugs (a render loop from a per-render `= []` default while TanStack data is undefined, and a percentage inside an SVG path `d`); new canvas UI must be run live in Playwright before merge, not just vitest.
- Frontend MSW keeps `onUnhandledRequest: "bypass"` (284 stray requests in 182 tests would need handlers to switch it; an open decision pinned as current behavior).
- Two frontend source-scan guards: `frontend/src/test/pages/pageScrollContainer.test.tsx` (every page under `AppLayout` needs the `h-full overflow-y-auto` wrapper; it reads the route table, parses each page with the TypeScript compiler, judges the exported component's LAST return, and stale-checks its allowlists `OUTSIDE_LAYOUT_PAGES` and `NO_PAGE_SCROLL_BY_DESIGN`) and `src/test/components/dialogCentring.test.tsx` (a source scan over the native dialogs; a NEW native dialog needs the `m-auto` class AND its file added to the known set).
- `test/routes.test.tsx` pins admin route membership STRUCTURALLY via `createRoutesFromElements` (no render): the exact 16-path guarded set, that the group sits under `AuthGuard` (AdminGuard returns null with no user, so losing the parent blank-pages anonymous visitors), no duplicate paths, and that the group renders an `Outlet`; guard detection searches the element subtree, so a wrapper around `AdminGuard` does not false-red it. Adding an admin route means adding it in FOUR places: the group, the Administration dropdown in `AppLayout.tsx`, that test's literal list, and `REMAINING_GUARDED_PATHS` in `tests/e2e/test_admin_guard_redirect_playwright.py` (one registered account walks every admin route there; do not write a per-page redirect test, auth has no user-delete endpoint so each such account persists). After touching the route tree, still run a live non-admin visit (the frontend live-gate recipe below). The nightly Selenium pins in `tests/e2e/test_register_and_roles.py` remain the black-box check.
- `src/test/flushPending.ts` (used inside `act`) is the ordering anchor for an absence check in a frontend test; see Test effectiveness rules.

## Unit-test harnesses and conventions

- Auth's HTTP test files share ONE harness (#511): importables (`engine`, `TestSessionLocal`, `override_get_db`, `mock_user`) in `services/auth/tests/_harness.py`, fixtures (autouse `setup_db`, `make_client(user)`, `use_reap_session_factory`) in `services/auth/tests/conftest.py`; a new auth HTTP test file should use these, not copy the engine block. Auth's HTTP tests that need the real claim path use `make_client()` with no user, which leaves `get_current_user` un-overridden (`test_effective_role_http.py`).
- Reservations has the same split (#628): `TEST_DATABASE_URL`/`engine`/`TestSessionLocal`/`override_get_db`/`override_bearer` live in `services/reservations/tests/_harness.py`, the autouse `setup_db` and `make_client` fixtures in `services/reservations/tests/conftest.py`, covering the six test files that carried the byte-identical block; nine files that read background-task state off `app.database`'s own engine (`test_fork_archive_reconcile.py` and siblings) keep private engines by design, mirroring auth's LDAP-sync exception. The LDAP-sync service/reaper/loop suites keep private engines by design (the reaper file must see the production `AsyncSessionLocal` default).
- Every service conftest (and the six test files that sign with their own literal, `services/common/tests/test_jwt_codec.py` among them) uses ONE 64-character hex test key, `3fcbb4bf16b0e162be24d2eb59065316c1e84194669ebf9270203280b18e18f7`, so no suite logs the short-secret warning; a test that signs with any key under 32 bytes gets `InsecureKeyLengthWarning` from PyJWT, which `filterwarnings = ["error"]` turns into a failure (sign with the shared key, or wrap the call in `pytest.warns` when the short key is the subject). `tests/integration/test_jwt_forwarding.py` asserts the stack's `AUTH_SECRET_KEY` is at least 32 bytes before it mints, with a message naming the length.
- `services/common/tests/test_jwt_codec.py` pins every JWT failure mode with its exact PyJWT class and message, the 401 over HTTP, the leeway on both sides of 10 s (5 s accepted, 12 s refused, for `exp` and `iat`), the short-key warning, and a token signed by python-jose 3.5.0 (a literal, so sessions survive a rolling deploy). `tests/unit/test_jwt_settings_wiring.py` (AST) guards PyJWT decode call sites and the per-service `config.py` token settings; its spellings and Limits are in its module docstring. The repo acceptance check for the PyJWT migration is that `grep -rn --include=*.py jose services tests` prints nothing.
- Consumer start tests: the `ensure_consumer`-then-`pull_subscribe` order per durable, and the stream each durable is created on, are pinned by each service's start test, with both calls read from ONE ordered log of (operation, durable) read BY DURABLE NAME (`durable_calls` on the notifications and integration fakes, and since #1181 a `durable_calls` list the execution test's `add_consumer` and `pull_subscribe` side effects append to, the durable read from the config at the `add_consumer` call). A fake that records the two calls in separate lists cannot see the order, a call-order check alone passes when some other durable was created, and a membership check over the streams cannot see them exchanged.
- The profile routes' rule that a caller whose effective role is `user` naming any other id gets the unknown-id 404 decided BEFORE any read of the named account is pinned at the database with a `before_cursor_execute` listener, never by patching a name, because `routers/admin.py` binds `get_user_by_id` by `from ... import`.
- A test pinning generation repair behavior must patch the setting `ai_generate_max_repairs` (`AI_GENERATE_MAX_REPAIRS`, default 2); the old hardcoded `MAX_REPAIR_ATTEMPTS` constant in `generator.py` is gone (`test_generate.py` is the pattern).
- `tests/unit/test_docs_nats_cli_form.py` fails on any tracked markdown or HTML whose DLQ command runs the nats CLI inside the `nats` service container, which has no CLI; the procedure that passes it is in [DEVELOPMENT.md](DEVELOPMENT.md).
- `tests/unit/test_manual_release_pages.py` fails when a page in `docs/manual/` does not carry exactly one release link in its header, pointing at the newest release page (by integer version) with the text `Release X.Y.Z`; when a release page's sidebar does not list every release page newest first with exactly one entry, its own, marked active; when a demoted release page's dek does not link the release immediately after it; or when a demoted release page contains one of four known expiring phrasings ("The current release is", "now describes", "now documents", "The version this manual documents"). It knows only those four phrasings, so a new way of saying the same thing passes, and it judges no other prose; the release-page rule is in [DEVELOPMENT.md](DEVELOPMENT.md) and the other limits are in the module docstring.
- Probing a Pydantic validator: mutate BEFORE `app.main` is imported or the route never sees it, and run a control that must fail.
- Cabling test seeding (`_seed_connection` helpers, the autouse `_no_device_group_guard` in test_connections.py) disables the device-group guard explicitly: a seed's 201 must never depend on the guard failing open because `inventory:8000` does not resolve.
- Test log output by asserting on `JSONFormatter(...).format(record)`, never on `caplog` text.
- Common's conftest gc.collects after every test so a leak fails AT the leaking test (see Known flakes, #534).
- Specification guard: `tests/unit/test_spec_references.py` fails on a dangling path, symbol, or test name in `docs/specs/`, so a rename must update the specification in the same PR. The guard checks only that a cited test EXISTS, not what it asserts or whether it is skipped, so split a rule whose test pins part of it. Since #1158 EXISTS means: for Python, a `test*` function in a `test_*.py` or `*_test.py` file, at module level or in a module-level `Test*` class with no `__init__`, not decorated as a fixture; for the frontend, the COMPLETE title of an `it`, `test`, or `describe` call in a `*.test.*` or `*.spec.*` file that starts its line, does not start inside a string or template literal, and is not commented out, `.skip`, `.todo`, or `.fails` (#1181). A title prefix, a helper or fixture (a `test_*` fixture included), a name left in a comment, and a node id all fail, and an Enforced in symbol left only in a comment fails too; a `unittest.TestCase` method in a class not named `Test*` and an inherited test method are refused conservatively. The word "withdrawn" in a rule's text exempts it from the reference checks (README convention 2); never use it casually.

## Integration, contract, and load tests

- Integration tests drive service-side failure paths through a double-gated fault-injection seam: `HERD_FAULT_INJECTION` (set only in `docker-compose.override.yml`, inert under `make prod`) plus a per-resource sentinel. The worked example is inventory's `update_device_status_internal` (a device named with `__herd_fault_status__` 503s its status update; see `tests/integration/test_provisioning_failed.py`). This is the inventory-side analogue of the driver-side `HERD_mock_*` knobs.
- The four hardware-free test drivers (`drivers/mock_l1/`, `mock_l2/`, `mock_l3/`, `mock_hypervisor/`) acknowledge port/VLAN/route/instance ops deterministically and expose `HERD_mock_fail_actions`/`HERD_mock_raise_actions`/`HERD_mock_sleep_ms` field_data knobs for failure injection. They drive the live `tests/integration/` coverage of L1 provisioning, VLAN assignment/release, L3 route provisioning (pinned-set removal), dynamic-resource provisioning, DLQ retention, and redelivery idempotency. `tests/unit/test_checked_in_drivers_structure.py` runs the structural check over every package under `drivers/`.
- `docker-compose.override.yml` pins several knobs for the live tests: `EXPIRATION_INTERVAL_SECONDS=5` (so sweep-dependent integration tests fit the 30s cap), `NATS_NAK_BACKOFF_SECONDS=0,1,1,1,1` (so `tests/integration/test_dynamic_resources.py`'s transient exhaustion stays inside its cap), `APPLY_SCHEDULER_INTERVAL_SECONDS=2` (for `tests/integration/test_config_apply_flow.py`, which schedules a real dry run on `drivers/frr_mgmt`; a dry run opens no SSH session), `WEBHOOK_ALLOWED_HOSTS=integration,reservations` (so the live tests' echo sink and the dead 404 target keep working), and an `ack_wait` of 4 s for INTEGRATION ONLY so `tests/integration/test_webhook_slow_receiver_live.py` fits the 30 s cap (sink `delay_ms=6000` on the test echo sink, which also counts arrivals per event id at `GET /webhooks/echo/hits`, admin token required; the sink's POST answers only in-network callers). `test_nats_consumer_configs_live.py` pins ack_wait per service and all five durables' server-side config.
- GOTCHA (issue #611): an integration test that publishes straight to JetStream (bypassing the outbox) MUST stamp a fresh payload `event_id` and set `Nats-Msg-Id` to it (`test_failed_teardown.py:_publish_event` and `test_health_alerting_flow.py` are the models). Without it the consumer's dedupe key falls back to `<stream>:<sequence>`, and since the compose `nats` service has NO volume, a container recreate resets sequences to 1 while Postgres keeps rows under those keys; the next run's inserts are then swallowed as redeliveries (unique on `(user_id, dedupe_key)`) and the test fails only on a reused stack. Reproduce with `docker compose -p herd-public-gate up -d --force-recreate --no-deps nats` then restart the consumer services.
- Integration tests confirm streams with `stream_info`, never `add_stream`.
- Integration tests must never forge a lifecycle event for a row reservations still holds ACTIVE (`test_failed_teardown.py` cancels for real; `test_event_verification_gate.py` is the inverted attack).
- A live redelivery test MUST bind a peer consumer (`pull_subscribe_bind`) or it passes with the heartbeat off, because a LONE pull consumer never receives its own redelivery (issue #944). That test's peer NAKs unrelated messages with a delay, and while its webhook exists every `reservation.created` on the stack is held 6 s, so it flakes on a stack other sessions are using. `tests/unit/test_consumer_heartbeat_wiring.py` guards the consumer heartbeat wiring; its module docstring lists its limits.
- Verify consumer latency changes with in-process message age (stream timestamp to receipt), not a synthetic probe: loopback probes on a synthetic stream do NOT reproduce the hold; only real load on a real stack does.
- Integration tests that create connections must use the `fresh_devices` fixtures, not fabricated UUIDs (pathfind-only tests may still fabricate), because cabling's POST /connections 422s when either device does not exist.
- A reservation created with one token is read back with THAT token (caller-token `GET /{id}` answers only the owner, admins included); a reservation whose start is inside `RESERVATION_START_GRACE_SECONDS` (300 s) activates in the create request, so a PENDING window needs a far-future start and a `_psql` move of `start_time` to `now()`. `make test-integration` runs pytest with `-x`, so one failure hides every later one.
- MODEL-DEPENDENT AI TESTS (issue #1270): an integration test that judges a live model's own tool-call choices carries `@pytest.mark.ai_model` (registered in `pyproject.toml`). `make test-integration` runs `-m "not ai_model"` with `-x`, and `make test-integration-ai` runs `-m ai_model` WITHOUT `-x`, right after it in both `master` and `everything`. These tests execute only on a host with an AI provider (ci.yml and nightly.yml set no `AI_*` env), where a small local model does not make the same choice every time; before the split one such miss stopped the whole suite under `-x`. The split isolates, it does not forgive: a marked test that fails still fails the gate, after every deterministic test has run. Marked today: `test_assistant_loop_response_shape_against_live_stack` (it checks every tool name the model emitted), `test_assistant_write_flow_discovers_schema_first` (tool order), and `test_assistant_answers_a_herd_how_to_from_the_manual` (search then read), all in `tests/integration/test_ai_assistant_tools.py`; `test_assistant_reservation_404_for_non_owner` is NOT marked, since its answer is decided before any model call. The rule is a test that calls `ai_provider_configured` AND reads the `tool_calls` field needs the marker; `tests/unit/test_ai_model_marker_wiring.py` enforces it, that at least one test is marked (`-m ai_model` selecting nothing exits 5), the registration, both pytest commands, and both gates' calls (its module docstring lists spellings and Limits). nightly.yml runs pytest over the whole directory with no `-m`, so it still collects the marked tests (they skip there). The docs-lookup test also retries ONCE, and only for one shape: the first turn called `search_docs`, no documentation tool errored, and no `read_doc` of `herd-manual` followed the first search; the same question is asked again and judged by the unchanged assertions, so a second miss in a row fails. A non-200, zero `search_docs` calls, or an erroring tool (the stale-image and empty-registry defects the test exists for) fails on the first turn. Do not widen that condition.
- The retry pollers (`_poll_retry_l1`, `_poll_retry_l2`, `_poll_retry_l3`) all delegate to `tests/integration/_wiring_retry.py::poll_wiring_retry`, which returns None unless the wanted outcome was seen; the `still_failed` polls pass no id and callers assert `still_failed`, while the post-clear convergence polls pass `failed_row_id` (the id of the row already seen FAILED) and then also accept that row from wiring-status BY ID when the retry answer no longer names it (`ACTIVE` for `reconnected`, `RELEASED` for `released`; a 200 without the row, or the frozen 409 on a terminal reservation, is what the background retry tick converging the row first looks like, #1158 item 6), so those callers assert `status`, not `outcome`. `RELEASED` by id does not say the driver ran (the supersession guard settles a release with no driver call and wiring-status shows it the same), so every caller that polls for `released` ALSO asserts a `SUCCESS` run of the release action after convergence (`remove_from_vlan` on the port, `disconnect_ports`): the shared apply writes the run before it flips the row, on both retry channels, and no such run can exist while the fail knob is armed; and the helper returns None at once when the retry reports the caller's own row `superseded`. A new `released` poll must carry the same run assertion. The helper is unit-tested in `tests/unit/test_wiring_retry_poll_helper.py` (scripted answers, the module's clock and sleep replaced); the fallback branch WAS RUN against a real stack on 2026-10-13 (dev stack, `WIRING_RETRY_INTERVAL_SECONDS=1`, a 3 s delay before the first retry POST): it ended both an L2 `reconnected` and an L2 `released` poll (the latter with its SUCCESS run assertion) and the tests passed; unforced, the manual retry wins the race every time; the L1 and L3 arms and the 409 arm are still unproven on a live stack: that run could not reach them because the stack's background tick was starved by stale rows, which #1190 fixed in the due selects, and nothing has re-run them since.
- The LDAP sync-now test is `test_concurrent_sync_now_runs_never_overlap` (accepts 202/409 or 202/202 and proves the two run rows do not overlap via `started_at` and `finished_at`); the heal-seam control anchors on the container clock (`select now()` after the create POST, the wiring_changed outbox row's `created_at` at or before it).
- Decisions left OPEN by the test sweep (pinned as current behavior): notifications' chat and webhook channels fail open on a transport error (the event is acked); cabling's single-create device-group guard fails open; the login form stays enabled while the config status loads.
- The webhook dead target in `tests/integration/test_webhooks_flow.py` answers a POST with 405 (a GET-only route), so the ledger assertion pins the row's own `response_status`, never a guessed code.
- `tests/integration/test_purpose_review_flow.py` never runs in CI (no `AI_*` env in ci.yml or nightly.yml), so its behavior is only observable on a local stack with a classifier. `tests/integration/test_ai_provider_wiring.py` pins the exact `/api/ai/status` key set; a new field means updating it. The integration test `test_assistant_write_flow_discovers_schema_first` asserts `pending_apply` is set IF AND ONLY IF some `schedule_config_apply` entry in `tool_calls` has `error` None: `tool_calls` records failed attempts too, and with the fixture device the schedule call is always refused. The topology PUT's `canvas_changed` compares the STRIPPED canvas, so integration tests that need a canvas change must edit a node-level or edge field, never `data.device` (`test_live_edit_topology.py` is the worked example).
- Load class `DeviceConfigUser` in `tests/load/locustfile.py` (weight 1; issue #1100): it picks the first Management device template (newest first) whose driver config schema answers `source: registry`, because its version bodies use the registry vocabulary and a driver-published schema (frr_mgmt, `additionalProperties: false`) would 422 every create and exit locust 1; one `load-cfg-<hex>` device of its own, deleted in `on_stop` (a 409 `device_in_use` cancels the listed reservations and retries once); it never applies or schedules. The locust `RoutedTopologyValidator` task no-ops without a seeded L3 switch.

## Teardown contract

- Every test, fixture, or script must delete a device's cables BEFORE the device, and before deleting or renaming a port (#1023). Integration fixtures (`fresh_device`, `fresh_devices`, the L3 switch fixtures) delete through `delete_device_checked` in `tests/integration/_device_teardown.py`: a leftover cable is removed and the delete retried, a refusal that cannot be cleared FAILS the test with the response body, and a lingering `device_in_use` is retried inside one 6 s budget per fixture and then FAILS the test too (`STRICT_IN_USE = True` since the #953 PR; a test that leaves a live reservation on a fresh device at teardown is a test bug). A new device-creating fixture must use that helper, never a bare ignored DELETE.
- Since #1158 the same holds for devices a TEST BODY or a session fixture creates (switches included): `delete_device_checked` for one, `delete_devices_checked(client, ids)` for several (every device gets its attempt before any refusal is raised, ONE shared in-use budget, one `DeviceTeardownError`), and `delete_port_checked(client, port_id)` for a port (204 or 404, else raises; it clears no cables, the test deletes a port's cables first).
- Cancel or release a reservation BEFORE deleting its topology; integration tests delete through `delete_topology_checked` in `tests/integration/_topology_teardown.py`, which fails the test on any refusal (no auto-cancel).
- The repo-root guard `tests/unit/test_integration_teardown_contract.py` ENFORCES it: an AST scan of `tests/integration/` that fails on an HTTP DELETE of one device, port, or topology outside the helpers, under the call spellings its module docstring lists (`client.delete`, a name bound to `client.delete` or to `getattr(client, "delete")`, `getattr(...)(...)` itself, any call naming the method `DELETE`, `client.stream` included) and the URL spellings (f-string, concatenation, `str.format`, `%`, a join over a list or tuple literal, with or without a query string or fragment after the id; a name bound to one by a plain, annotated, or augmented `+=` assignment, a walrus, a tuple unpack, or as a `for` loop or comprehension target; a parameter of a local wrapper, a `def` or a lambda assigned to a name, #1181). Its `ALLOWED` table is per (file, function, kind) with a COUNT and a reason: the three helper functions and the nine functions in `test_device_delete_guard.py`, `test_port_cabling_guard.py`, and `test_topology_delete_guard.py` whose subject is the delete's answer. A new subject test that sends its own DELETE needs an entry; a new delete in an exempt function, or one fewer, changes its count and fails; an entry nothing matches fails as stale; an exempt helper that RETURNS the answer (`ANSWER_RETURNING_HELPERS`, today `_delete_when_released`) must never be called as a bare expression statement, which is the only dropped answer the check sees (an answer assigned and never read, `_ = ...`, `asyncio.gather`, or a call through an alias is not seen; read the answer anyway).
- Limits (module docstring, #1181): names are read without regard to statement order, so a URL variable rebound to another URL can be reported for the wrong delete and can change an exempt count; a URL is followed through ONE local wrapper called by name (not two levels, an attribute or method wrapper, `functools.partial`, or a default parameter value); a dict lookup, an attribute, a call result (`httpx.URL`, `os.path.join`), `str.join` over a generator, a loop over `zip`, `enumerate`, or a dict, a doubled slash, `"delete".upper()`, and a wrapper forwarding `*args` are not resolved.
- A test whose body cancels its reservation must ALSO cancel it in the `finally` (a second cancel on a terminal row is a no-op), and cleanup that follows a checked delete in the same `finally` goes in a nested `finally`, so a refusal does not skip it. Template, driver, group, and connection deletes in teardown are still bare and unguarded.
- The helpers are unit-tested stack-free in `tests/unit/test_device_teardown_helper.py` (`httpx.MockTransport`, a fake clock for the in-use budget). `conftest.py` imports the helper top-level (`from _device_teardown import`) while test files import it package-relative, so it has two module identities; catch `DeviceTeardownError` from the same import path that raised it.
- Frontend wording for the refusals goes through `deletePortErrorText` and `topologyDeleteErrorText` in `lib/errors.ts`.

## End-to-end tests (Selenium and Playwright)

- E2E is Selenium + Playwright: NEW e2e tests use Playwright's Python sync API via the `pw_browser`/`pw_page`/`pw_contexts` fixtures in `tests/e2e/conftest.py` (NOT the pytest-playwright plugin: its `browser` fixture is shadowed by the Selenium conftest's `browser` fixture for everything under `tests/e2e/`); the Selenium suite stays and is ported only opportunistically. Playwright runs host-side against `E2E_HOST_BASE_URL`, unlike the Selenium container.
- New tests must assert the backend-observable EFFECT via API read-back after each UI action, not just UI acknowledgment, and restore any mutation to baseline (`tests/e2e/test_config_playwright.py` is the worked example, including the config.bootstrapped precedence-marker restore).
- GOTCHA: a worktree has no `.env`, and the e2e conftest reads the admin credentials from the repo-root `.env` of the checkout pytest runs in, so a Selenium or Playwright run from a worktree fails at LOGIN for every test unless the main checkout's values are exported first (`set -a; . ./.env; set +a` in the main checkout, then pytest in the worktree).
- `make test-e2e` installs the Playwright chromium (cached no-op; a fresh host may need `--with-deps`). `docs/MANUAL_TESTING.md` is the companion checklist of deliberately-unautomated cases; consult it before proposing automation for anything it lists.
- GOTCHA: Playwright's `get_by_text` is a SUBSTRING match by default, so `get_by_text("reachable")` also matches "unreachable" and asserts nothing; pass `exact=True` whenever one state's label contains another's.
- Selenium gotcha: the `standalone-chrome` e2e container caps at 3 sessions; a probe or fixture that creates a driver and raises before it is quit leaks a slot until `docker compose --profile e2e up -d --force-recreate selenium`, and the symptom is spurious login timeouts mid-suite. Since #1266 the conftest's `browser`, `logged_in_browser`, and `admin_browser` fixtures open their driver through `_open_selenium_driver`, which registers `driver.quit` with `request.addfinalizer` before the login runs, so a login that raises no longer leaks: pytest runs that finalizer at the end of the module even though the fixture failed. A new fixture that creates a driver goes through the same helper.
- E2E failure artifacts: any e2e test that fails in its CALL phase leaves screenshot.png, page.html, console.log, traceback.txt, and meta.txt under `HERD_E2E_ARTIFACT_DIR` (default `<tempdir>/herd-e2e-artifacts/<sanitized nodeid>/`); the pytest failure output and sessionfinish name the directories. On any gate e2e failure READ THESE FIRST; do not touch timeouts or assertions without them. Since #1266 a test that fails in its SETUP phase (a fixture raised, a login timeout above all) leaves the same files under the same name prefixed `setup-` (`setup-<sanitized nodeid>/`) for every page or driver created during that test's setup (`pw_page` and `_open_selenium_driver` register theirs with `register_setup_browser`; the fixture's own teardown runs after the hook, so the page or driver is still open), else for what the test's already-resolved fixtures hold (the call-phase lookup: `pw_page`, every open page of `pw_contexts`, or a Selenium driver, such as a module-scoped driver an earlier test created), else only traceback.txt, an empty console.log, and a meta.txt whose last line begins `no page or driver was registered or resolved for this test`. The text-only causes: a hub that never answered or a fixture that raised before any browser existed, and every test after the first in a block of one module-scoped fixture's error, because pytest re-raises the cached error without resolving the fixture again (the driver is still open, held until the module ends, but this test never received it). The registry is emptied after every phase of every test. Nothing is written for passing tests, skips, or teardown-phase failures. Every page.html has the value of each password input replaced by `[redacted]` (React reflects a controlled input's value into its `value` attribute, so a login page that timed out after the form was filled would otherwise carry the password); the scan tokenizes each input's attributes, so text inside another attribute is never taken for `value` or `type`. `ADMIN_PASSWORD` is a `_Secret`, a `str` whose repr is `'[redacted]'`, and `pw_login`, `_do_login`, and `_open_selenium_driver` rebind the password they receive as one, so pytest's printed frame arguments (`--tb=long`, the first and last frames under `--tb=auto`) and `-l` locals show `'[redacted]'` in the terminal and in traceback.txt; a password a test keeps in its OWN local or argument is not covered. Selenium sessions ask for `goog:loggingPrefs` browser ALL and the hook reads the log with the getLog command (`webdriver.Remote` has no `get_log`); when the Grid refuses it, meta.txt carries a `console:` line with the error. A test that needs MORE THAN ONE browser context must create them through the `pw_contexts` pool fixture and must NOT close them itself: a context closed in the test body (or a bare `pw_browser.new_context`) is gone before the hook fires, so nothing gets captured (test_two_session_port_conflict is the worked example). The hook uses new-style `@pytest.hookimpl(wrapper=True)`; do not revert it to `hookwrapper=True` (an escaping BaseException under `filterwarnings = ["error"]` becomes an INTERNALERROR that destroys the whole session's results). Nightly uploads the per-test e2e artifact dir (`HERD_E2E_ARTIFACT_DIR` set into the workspace, pinned by `tests/unit/test_nightly_e2e_artifacts_wiring.py`).
- Reused-stack e2e skips (issue #670): `test_topology_validator.py` picks `tmpls[0]` and `test_connections_bulk_playwright.py` picks the first device pair, so on a stack that has been through load tests or repeated passes they SKIP (422 unknown fields; too few free ports). Both pass on a fresh gate seed, so `make everything` is unaffected; a skip seen only on a reused stack is stack history, not a regression.
- The first e2e phase of `make everything` and `nightly.yml` runs BEFORE `make seed`, so device-gated Playwright tests (fork restore, network elements) SKIP there by design. Since #629 a SECOND pass, `make test-e2e-seeded`, runs right after the gate seed (and after nightly's seed step) with `HERD_E2E_REQUIRE_NO_SKIP=1`: `tests/e2e/conftest.py` collects every skip (setup-phase fixture skips included) and FAILS the run if any non-exempt skip remains, printing node id and reason. A skip that is expected even on a seeded stack carries `@pytest.mark.seeded_skip_ok(reason)` (registered in `pyproject.toml`; `filterwarnings = ["error"]` makes an unregistered marker a collection error): the LDAP-login tests (gate stack is `AUTH_METHOD=local`), the five AI-gated tests (nightly has no `AI_*` env), and two deliberately-manual placeholders. Exempt skips still print under their own heading. Both passes share the `_test-e2e-run` Makefile helper so they cannot drift; `master` has no seed phase and is unchanged. `tests/e2e/test_network_elements_playwright.py` needs a SEEDED stack, which the `test-e2e-seeded` pass provides (#629). The L3 routing e2e test's fixture owns every cleanup via an accumulated list replayed on skips and teardown; it carries NO `seeded_skip_ok` on purpose.
- E2E does NOT run in per-PR CI (only `backend`, `frontend`, and the advisory contract plus integration job do); the e2e suite runs in `nightly.yml`. A UI change can therefore be green on every check that actually executed and still break e2e. After changing a DEFAULT UI surface, grep `tests/e2e/` for every test that opens it, not just the one you updated.
- Live-gate gotcha: a service container's uvicorn `--reload` fires on plain edits but did NOT fire on git-driven file swaps (`git stash` push/pop), so the process keeps serving pre-swap code while the mounted file shows the new content. When toggling code via git during a live gate, `docker compose restart <svc>` and verify, never trust hot reload.

### Running a frontend branch's e2e against a live stack before merge

In its worktree run `uv sync --all-extras` (else pytest dies on `Unknown config option: asyncio_mode`), write a throwaway `vite.live.config.ts` that `mergeConfig`s the base with proxy target `https://localhost` and `secure: false` (the checked-in proxy targets plain http), run `npx vite --config` it with `VITE_HERD_BUILD` set, then pytest with `E2E_HOST_BASE_URL=http://localhost:5173`; never stage the throwaway config. After swapping code under a running stack, an `/api/<svc>/` path that returns the frontend's `index.html` means that service is DOWN and the request fell through to the catch-all route, not that routing is wrong. For the live non-admin visit after touching the route tree: worktree, `npx vite --port 5173` with the proxy pointed at `https://localhost` `secure: false`, Playwright with `E2E_HOST_BASE_URL=http://localhost:5173`, never touching the gate containers.

### E2E login timeouts are a known flake class (issue #1266, open)

About one e2e run in seven fails in a LOGIN fixture with a timeout (Selenium `TimeoutException` in `_do_login`, or Playwright `pw_login`'s `wait_for_url("**/topology**")` at 30 s) while the same run's other login-driven tests pass. The Selenium form comes as a block of consecutive `ERROR at setup` in one module: pytest caches a module-scoped fixture's error and raises it again for every later test of the module that requests the fixture, without running the fixture again, so a block is ONE login failure, and only its first `setup-` artifact directory holds the page (the 2026-10-21 and 2026-10-30 blocks, 4 and 5 errors, are exactly the tests in `tests/e2e/test_user_groups.py` and `tests/e2e/test_topology_editor.py`). Since the issue's three changes, a login failure says what happened instead of a bare timeout. `pw_login` clicks inside `expect_response` on `POST /api/auth/login`: a request that never answers fails there, a non-200 fails at once with `POST /api/auth/login answered <status>, expected 200: <body>` (the password redacted from the body), and only a 200 goes on to wait for /topology with `wait_until="commit"`. `_do_login` fails with `the login form (#login-email) did not render`, or with `login did not reach /topology within 15s; the page is at <url>; POST /api/auth/login statuses the page received: <list>` (`none` when no login response arrived; read from the page's Resource Timing entries, since Selenium cannot wait on the request). When the login runs inside a fixture, the failure writes the `setup-` artifacts above; when it runs in a test body (most `pw_login` calls, and `_do_login` in `tests/e2e/test_register_and_roles.py`) it is a call-phase failure and writes the unprefixed directory. A Selenium driver whose login raised in a fixture is quit at the end of the module. These changes make the next occurrence diagnosable; they do not remove the flake. Triage: one such error (or one such block) in an otherwise green run is this class, read its artifact directory (the first one of a block), rerun the gate; the same fixture failing twice in a row is not.

## E2E gotchas

### Toast placement and pointer parking (issues #938, #942)

Toasts render at the BOTTOM CENTRE since issue #942 (`<Toaster position="bottom-center" />` in `App.tsx`, pinned by `src/test/App.test.tsx` and `tests/e2e/test_toast_placement_playwright.py`, which measures real boxes at 1280x720 and 1920x1080 with one toast and a stack of three), so a toast no longer covers Save or the header. react-hot-toast still pauses a toast while the pointer is over it, so a test that waits for the toast stack to empty must first park the pointer outside the toaster: the left edge, `(5, 400)`, is clear of any centred toast (a success toast is at most 350 px wide, the fork save custom toast about 450 px) (`_click_save` in `tests/e2e/test_l3_routing_playwright.py` and the `_park_pointer` helpers are the worked examples; a point near the bottom centre is INSIDE the stack). The page-end controls on `/config` and `/templates/new` sit above a `pb-56` clearance from `TOAST_CLEARANCE_CLASS` in `src/lib/toastClearance.ts` (issue #988).

### Saved preferences and filters (issues #938, #951, #1070)

- A test that types in the inventory search must wait for the debounced preference PATCH before restoring the saved filter, or the late PATCH poisons the next run (`test_inventory_expansion_survives_delayed_search_refetch`). The same holds for EVERY saved preference an e2e test touches (issue #951): the Reservations sort persists under `extras["sort:reservations"]`, so a test that clicks a sort heading must reset it to the default first (a "two clicks reach descending" assumption breaks on the second run), wait for the debounced PATCH carrying its final choice, and restore the baseline in a `finally`.
- An e2e reservation is cleaned up by CANCELLING, which leaves the row in the list, so its purpose text needs a per-run suffix and an `exact=True` match (`tests/e2e/test_reservations_sort_playwright.py` is the worked example).
- E2E on a shared stack: compare an UNFILTERED view to the body of the list response the page itself received, never to a separate API read, because the unfiltered total moves under other sessions.
- Preference PATCH predicate (issue #1070, PRs #1072 and #1073): wait for a saved-filter PATCH through ONE predicate, `pw_prefs_patch_carries` in `tests/e2e/conftest.py`, which compares the parsed body's `saved_filters[page]` by equality; a substring match on a raw request body matched an earlier, longer search and leaked it into later tests, and `tests/unit/test_e2e_prefs_patch_predicate.py` scans `tests/e2e` and fails on a substring test against a request body. The Selenium search test reads the saved filter first and restores it in a `finally`.

### Wiring retry convergence (issue #953)

ONE manual wiring retry does not always converge. Execution's background retry tick (`WIRING_RETRY_INTERVAL_SECONDS=60`, wall-clock from service start, not overridden in the dev stack) can be driving a test's FAILED rows at the moment the test clears a mock fail knob; the tick then fails them, and a manual "Retry failed" click that lands before the tick records its result loses the row claim (#817, outcome `in_progress`), so the rows stay FAILED until the next retry. A test that clears a fault and retries must click again when the read-back does not converge (`_retry_until_active` in `test_wiring_layered_playwright.py` and `test_wiring_failed_row_playwright.py`), never rely on one click plus a long poll.

### Anchoring a read-back on the action's own response (issue #1169)

A wait that orders an API read-back must be something ONLY the action under test can produce, and a toast is not that once an earlier action has put the same text on screen. Lifetimes (react-hot-toast defaults, `<Toaster>` sets none): a `toast.custom` (the fork save toast) stays 4 s, a `toast.success` 2 s, and each stays in the DOM about 1 s more for its exit, so a test that saves twice inside that time finds the first toast still up: the second wait returns at once and the read-back races the request still in flight (the 2026-10-11 nightly, `test_restore_then_save_via_fork_readback_pw`, `assert 2 == 3`, lost by 7 ms), or both toasts match and Playwright raises a strict mode violation. The anchor is the action's own HTTP response, because the server commits before it answers: `pw_click_for_response(page, target, method, url_end, status=200)` in `tests/e2e/conftest.py` waits for `target` to be enabled, clicks INSIDE `page.expect_response` (so a response that arrives at once is still caught), asserts the status, and returns the response; assert a server-allocated value from its body where one exists (`version_number`). It returns the FIRST matching response, and the main axios client replays a request once after a 401 and a token refresh, so a test that outlives its access token (30 minutes; `pw_page` gives each test a fresh browser context and every current caller signs in at its start) writes its own `expect_response` whose predicate also requires `r.status != 401`.

A toast stays a UI assertion only, and only when it can be met by this action's toast alone: either its text is unique to the action (`_pw_commit_fork` in `test_fork_live_edit.py` asserts `Fork saved as v<n>` with `exact=True`) or the earlier toast is proven gone first with `pw_toast_gone(page, text)`, which parks the pointer at `PW_OFF_TOASTER` and waits for count zero over the whole page (about 3 s after a success toast; hidden is not gone). Worked examples: `_pw_commit_fork`, `_ui_save` in `test_config_playwright.py`, `_save_config_version` in `test_flows_effects_playwright.py`. A custom toast carries no `role="status"`, so `_click_save`'s `[data-rht-toaster] [role='status']` drain in `test_l3_routing_playwright.py` does NOT see the fork save toast. To hold a browser request back in a scratch reproduction, delay it inside the page (`page.add_init_script` wrapping `XMLHttpRequest.prototype.send`); a `time.sleep` in a sync Playwright route handler blocks the test thread as well and hides the race.

MUTATION PROOF RUN 2026-10-13 on a seeded gate stack (the save held in the page by an `add_init_script` XHR wrapper, 1500 ms): the old toast wait fails `test_restore_then_save_via_fork_readback_pw` with `assert 2 == 3` and `test_config_full_cycle_edit_and_restore_via_ui` with a stale read-back, and the fixed waits pass under the same delay; `test_config_save_persists_value_via_api_readback` and `test_device_config_version_cycle` pass under the old wait even at 3000 ms (no earlier toast exists, or a visible-row wait already orders them), so there #1175 is defense in depth.

LIVE-RUN TRAP: the config e2e tests' `preserve_precedence_marker` probes with `docker compose exec` in the checkout pytest runs from, so from a worktree, or with a `COMPOSE_PROJECT_NAME` that does not match the stack, the probe finds no container and the UI save's deletion of `config.bootstrapped` is never undone; never run them against a stack that must keep its config from anywhere but the checkout and project that own it.

### datetime-local (issue #1100)

Chromium keeps a `datetime-local` value in its shortest form, so filling `2026-10-15T20:49:00` stores `2026-10-15T20:49` and Playwright's `fill` raises `Malformed value` (a one-in-sixty chance for a time computed with seconds). Build the value without a seconds part when the seconds are zero, and compute it in the page (`page.evaluate`) so the browser's time zone, not the host's, decides the ISO instant (`_LOCAL_AHEAD_JS` in `test_device_config_apply_playwright.py`; the conversion is exactly `new Date(local).toISOString()`, as `DeviceConfigSection.tsx` sends it). Known, unfixed: the repeated hour of a DST fall-back resolves an hour early (local runs only; nightly and the gates run in UTC).

### Template editor Save (issue #988 follow-up)

## Test effectiveness rules

The 2026-10-09 sweep (issues #1134 to #1148, #1152, #1158; PRs #1149 to #1151 and #1153 to #1157) read every test file in the repo for whether it proves what it claims, verified 75 HIGH findings adversarially by mutation, and landed the fixes with a MUTATION PROOF in each PR.

### The mutation-proof bar

The fixed test FAILS with the guarded code changed (a scratchpad-only pytest plugin passed with `-p`, or a scratchpad vitest config aliasing a mutated copy; never a plugin in the repo) and PASSES without. Keep that bar for any PR that fixes a test.

### Shapes the sweep found and the rule each became

- An arranged input that fails an EARLIER check (a driverless device template 422s on the driver rule whatever the field under test says) means the payload must be valid except for the one rule, with the exact detail asserted.
- A read-back through a route that strips or redacts (every canvas GET) proves nothing about the WRITE, so read the stored row.
- An ordering test inserts newest first with distinct timestamps (SQLite CURRENT_TIMESTAMP ties at one second and an unordered SELECT returns insertion order).
- A concurrency test holds the first writer open (an asyncio.Event at its UPDATE, a barrier) or it pins scheduling, not the invariant.
- An absence check awaits an ordering anchor (the frontend's `src/test/flushPending.ts` inside `act`, an execution-observable stamp such as `last_applied_fork_version`, a later reservation's event) and never a fixed sleep read synchronously after the click.
- A fake must not implement the behavior under test.
- A Selenium assertion reads the changed element with exact text, never a whole-body substring (every static label satisfies "name", "port", "device a").
- A Playwright wait that orders a read-back is the action's own response (`pw_click_for_response`), never a toast an earlier action could have raised (#1169).
- A status-only assert on a test whose name claims a detail is a finding.

### Product defect found by the sweep (#1152)

The losing FAILED-to-ACTIVE CAS writer in all three wiring ledgers read `reusable.id` AFTER `db.rollback()`, which expires every loaded instance, and raised `MissingGreenlet` instead of returning the winner's row; the id is now captured before the UPDATE (`reusable_id`) in `record_route_active`, `record_l1_connect`, and `record_l2_membership_active`, pinned by tests whose loser's row is attached to its OWN session (a row from a closed session hid the bug).

### Recipe rules

- The authoritative list is the `_gate-pg-live-tests` recipe in the Makefile; `tests/unit/test_pg_live_gate_wiring.py` fails if any `services/*/tests/*_live_pg.py` is not RUN by it, so a new pg-live suite must be added to that recipe in the existing shape: `(cd services/<svc> && HERD_TEST_PG_REQUIRED=1 HERD_TEST_PG_DSN="$$dsn" uv run pytest tests/<file> -v)` joined to its neighbors by `&&`.
- Since #1158 the guard parses the recipe's commands. The variable must be on the pytest command itself (an `export` once for the line is refused), and only `HERD_TEST_PG_REQUIRED` and `HERD_TEST_PG_DSN` may be assigned there (`PYTEST_PLUGINS`, `PYTHONPATH`, anything else refused, #1181), the command must run in the suite's service directory, and every argument besides the file must be on the guard's short allowlist of options that cannot narrow or skip a run (`-v -q -x -s -l`, `-r<chars>`, `--tb`, `--durations`, `--durations-min`, `--maxfail`, `--color`, `-W`, `-p no:<plugin>`, `--strict-markers`, `--strict-config`): `-k`, `-m`, `--collect-only`, `--deselect`, `-o`, a node id, and `PYTEST_ADDOPTS` anywhere in the recipe or on any make-level line of the Makefile outside a comment fail it, as do a target-specific `SHELL` for the phase, a `;`, `||`, `|`, or `&` AFTER the command (so `|| true`, and a `;` after a `fi`, `done`, or `esac` around it; the recipe's own `dsn=...;` assignments AHEAD of the commands are fine), the command on the right of `||` or `|`, a `-` line prefix, and ANY `exit` or `exec` word anywhere in the recipe ahead of the command, in any position (an honest `test -f .env || exit 1` is refused too, by decision, #1181). An unterminated quote fails with an assertion naming the recipe line. `env -u VIRTUAL_ENV uv run pytest ...` and `timeout <n> uv run pytest ...` are read through.
- The same file pins that `master` and `everything` each call the phase through `$(MAKE)`, `$(SUBMAKE)`, or `make` with no `-n`, `-q`, `-t`, `-i`, or `-o`, no `NAME=value` before or after it (`MAKEFLAGS=n`, `SHELL=true`, even a harmless `COMPOSE_PROJECT_NAME=...`), no `-C`, no `exit` or `exec` word ahead of it in the gate's recipe, and no target-specific `SHELL` on the gate (#1181). What the scan cannot see (a `trap`, `.IGNORE`, a second definition of the target, a global `SHELL`, `.SHELLFLAGS`, `MAKEFLAGS` in the Makefile, an `include`, environment and command-line variables) is listed in its module docstring; a prerequisite-only rule line above the recipe reads as an empty recipe (a false red).
- GOTCHA (issue #819): every `_gate-pg-live-tests` suite runs AFTER the seeded e2e pass against the gate's USED ledger, so it must tolerate foreign rows: the suite scopes the tick's three `due_failed_*` lookups to its own reservation by wrapping the real queries (never replacing the SQL), snapshots every other reservation's rows before and after, and pre-selects with a limit no gate ledger reaches. Prove a new pg-live suite on a Postgres seeded with foreign rows first, then on an empty one; a throwaway empty database alone proves the wrong shape.
- Row-claim tests: `test_wiring_retry_claim_race_live_pg.py` runs both retry channels as real concurrent tasks; `test_sweep_claim_cancel_race_live_pg.py` races the sweep claim against a real cancel in both orders. The retry-only due selects use `FOR UPDATE SKIP LOCKED` with `of=<Model>.__table__` (the ledger table only); never `of=` the mapped class, which renders an alias Postgres rejects once a live suite has flipped `__table__.schema` under an already-built mapper.
